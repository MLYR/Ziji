# ADR-024：工程工具链与工作区

- 状态：已接受
- 日期：2026-08-13
- 决策任务：ENG-DEC-001
- 影响范围：仓库根目录、backend、web、mobile、packages、scripts

## 背景

资迹 V1 已冻结 Spring Boot 模块化单体、React/Vite Web、React Native/Expo Mobile 和 OpenAPI 同源类型。工程开工前仍需确定 Java 构建工具、JavaScript 包管理器以及单仓目录和依赖边界。

决策需要满足：

- 后端能稳定执行 Spring Boot、Flyway、jOOQ 与 Testcontainers 构建生命周期。
- Web 与 Mobile 共用 OpenAPI 生成类型和少量无平台依赖工具，但不共享界面组件或财务算法。
- 新环境使用仓库内固定入口，不依赖开发者全局安装的 Maven 或不同版本包管理器。
- 不引入与 V1 规模不相称的构建编排平台。

## 决策

### 1. 后端使用 Maven Wrapper

- 后端采用单个 Maven 工程，Spring Modulith 业务边界通过 Java package/module 约束和架构测试表达，不拆成一组独立部署模块。
- 工程创建任务 `ENG-BE-001` 负责提交 Maven Wrapper，并固定可支持 Java 25 与 Spring Boot 4 的 Maven 3.9.x 版本。
- Flyway 迁移继续位于 `backend/src/main/resources/db/migration/`；jOOQ 生成代码是构建产物，不手工维护。

选择理由：Spring Boot、Flyway、jOOQ 和 Testcontainers 的 Maven 集成成熟；资迹后端是一个模块化单体，Maven 的单工程生命周期足够直接。相比 Gradle，当前团队没有需要自定义构建逻辑或大规模多模块增量构建的证据。

### 2. JavaScript 使用 pnpm workspace

- 根目录固定 `packageManager: pnpm@10.4.1`，Node.js 基线为 22.22.3。
- workspace 只包含 `web`、`mobile` 和 `packages/*`。
- Web 与 Mobile 仍是独立应用，分别拥有自己的依赖、脚本和平台配置。
- `packages/api-types` 只承载由 `openapi-typescript` 生成的同源 API 类型及其发布边界；生成文件不得手工修改。
- 不建立跨平台 UI 包，不共享 React DOM/React Native 组件，不在客户端共享账务计算实现。

选择理由：pnpm 对单仓多应用提供严格、节省空间且可复现的依赖安装；workspace protocol 能明确共享生成类型。相比 npm workspace，pnpm 的依赖隔离更适合同时存在 Vite 和 Expo；相比 Yarn/Bun，当前没有迁移收益足以承担额外兼容面。

### 3. 使用单 Git 仓库，不引入额外编排器

```text
backend/                  Spring Boot 模块化单体
web/                      React + Vite 应用
mobile/                   React Native + Expo 应用
packages/api-types/       OpenAPI 生成的共享 TypeScript 类型
openapi/                  机器契约
scripts/                  跨工程开发和校验脚本
doc/                      产品、设计、架构和 ADR
prototypes/               UI 评审原型
```

V1 不引入 Nx、Turborepo、Bazel 或独立组件仓库。根脚本只编排明确的 pnpm/Maven 命令；CI 按目录并行执行。出现可量化的构建瓶颈后再以新 ADR 评估编排器。

## 被否决方案

| 方案 | 未采用原因 |
| --- | --- |
| Gradle Kotlin DSL | 当前没有复杂构建逻辑需求；会增加一套团队学习和插件调试成本 |
| npm/Yarn/Bun workspace | npm 隔离较弱；Yarn/Bun 未体现对当前 Expo/Vite 组合的必要收益 |
| Web 与 Mobile 独立仓库 | 会增加 OpenAPI 类型版本漂移和跨端变更协调成本 |
| 共享 UI 组件包 | React DOM 与 React Native 原语不同，强行共享容易形成平台条件分支和可访问性退化 |
| Nx/Turborepo | 当前工程规模尚无缓存和任务图收益证据，YAGNI |

## 后果

正向影响：

- 一个仓库即可完成契约、后端、Web 和 Mobile 的原子评审。
- Maven Wrapper 与固定 pnpm 版本降低环境漂移。
- API 类型共享而 UI/账务逻辑不共享，边界清晰。

约束与成本：

- 根锁文件变更可能同时影响 Web 与 Mobile，评审时必须检查作用域。
- pnpm 升级、Node 主版本升级或 Maven 大版本升级必须由独立任务验证 Expo、Vite 和后端构建。
- `ENG-BE-001`、`ENG-WEB-001`、`ENG-MOB-001` 完成前，根目录只提供仓库骨架，不宣称应用可以启动。

## 验证

1. `pnpm-workspace.yaml` 能识别 `web`、`mobile`、`packages/api-types`。
2. 根 `package.json` 固定 packageManager 和 Node engine，不包含业务依赖。
3. `.gitignore` 覆盖 Java、Node、Expo、Vite、IDE、系统文件和本地密钥。
4. Git 初始化后，现有 `.DS_Store`、`.idea/workspace.xml` 和本地环境文件不会进入待提交清单。
