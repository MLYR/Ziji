# 资迹 Ziji — 数据库设计

**文档版本：** V0.1  
**对应产品版本：** V0.1  
**需求基线：** PRD V0.1、RTM V0.1、核心领域与账务设计 V0.1  
**数据库：** PostgreSQL  
**文档状态：** V1 正式逻辑设计基线

## 1. 设计目标

数据库设计需要保证：

- 交易、分录、余额和持仓可追溯、可重建
- 已确认账务不可被普通业务操作物理删除
- 共享账户权限和历史计入比例可按时点查询
- 同步、导入和外部行情具有幂等约束
- 敏感凭据不以可直接使用的明文保存

本文是逻辑模型，不替代 Flyway 迁移脚本。所有表结构最终以经过评审的迁移文件为准。

## 2. 数据库约定

### 2.1 命名和主键

- 表名、字段名使用 `snake_case`
- 业务主键使用 UUID，由应用生成
- 客户端可创建实体使用客户端生成的 UUID
- 单调同步游标使用 `bigint generated always as identity`
- 所有外键显式命名并建立必要索引

### 2.2 通用类型

| 语义 | PostgreSQL 类型 |
| --- | --- |
| 时间戳 | `timestamptz` |
| 业务日期 | `date` |
| 金额 | `numeric(24,8)` |
| 数量、价格、汇率 | `numeric(28,12)` |
| 比例 | `numeric(9,6)` |
| 币种 | `char(3)` |
| 枚举 | `varchar` + CHECK，避免迁移困难的数据库 enum |
| 可扩展载荷 | `jsonb`，只用于外部原始数据或同步载荷，不替代核心列 |

金额通过数值和借贷方向表达，不用正负值表达 LedgerEntry。

### 2.3 通用审计字段

可修改业务表至少包含：

```text
created_at timestamptz not null
created_by uuid null
updated_at timestamptz not null
updated_by uuid null
version integer not null default 1
```

删除/作废采用业务状态或 `deleted_at` 墓碑；账务事实表禁止普通软删除字段被随意修改。

### 2.4 金额约束

- 金额和数量按字段语义设置 `CHECK (value >= 0)` 或 `CHECK (value > 0)`
- 比例设置 `CHECK (ratio between 0 and 1)`
- V1 币种设置 `CHECK (currency in ('CNY','USD','HKD','JPY','EUR'))`
- Java 写入使用 BigDecimal 字符串，禁止经过 double

币种入账精度：CNY、USD、HKD、EUR 为 2 位小数，JPY 为 0 位小数。数据库保留 `numeric(24,8)` 作为统一存储容量，但 LedgerEntry、手续费、税费和实际成交金额写入时必须满足对应币种最小单位。

通过不可变函数 `currency_minor_units(currency)` 和受控触发器校验：

```text
amount = round(amount, currency_minor_units(currency))
```

数量、价格和汇率最多 12 位小数；持仓成本最多 8 位小数；比例和收益率最多 6 位小数。统计投影先使用原始允许精度聚合，再按投影基准币种最小单位舍入一次。

### 3.2 email_challenges

用于注册和密码重置。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | PK |
| purpose | varchar(20) | REGISTER/RESET_PASSWORD |
| email_normalized | varchar(320) | NOT NULL |
| code_hash | varchar | 验证码 Hash，不保存明文 |

约束：`expires_at = created_at + 10 minutes`，V1 `max_attempts=5` 且 `attempt_count <= max_attempts`；`consumed_at` 与 `invalidated_at` 不得同时存在；`invalidated_at` 和 `invalidation_reason` 必须同时为空或同时有值，且失效时间不得早于创建时间。同邮箱、同用途至多一个活动挑战；应用在同一事务内将旧活动挑战标记为 `REPLACED` 并写入新挑战和投递事件，任一步失败均整体回滚，不物理删除历史挑战。

### 3.2.1 auth_rate_limit_buckets

认证验证码发送和密码登录共用 PostgreSQL 固定窗口桶作为跨实例权威，不能建立第二套限流事实表。验证码按 `REGISTER`、`RESET_PASSWORD` 隔离；密码登录使用独立 `LOGIN_PASSWORD/LOGIN/AUTH_LOGIN_V1` 作用域。每个请求按冻结顺序原子 UPSERT/锁定全部窗口，超限请求也提交 `request_count`，不允许先查后写。

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| id | uuid | PK |
| action | varchar(40) | `SEND_EMAIL_CHALLENGE/LOGIN_PASSWORD` |
| purpose | varchar(20) | `REGISTER/RESET_PASSWORD/LOGIN` |
| dimension | varchar(12) | `IP/EMAIL/DEVICE`；密码登录只允许 `IP/EMAIL` |
| subject_hash | bytea | 固定 32 字节 HMAC-SHA-256 摘要，不保存原始 IP、邮箱或 deviceId |
| hash_key_version | smallint | 外部 HMAC 密钥版本；轮换期间当前及上一版本均参与识别，上一版本至少 48 小时 |
| policy_code / window_code | varchar | 固定策略和窗口标识 |
| window_seconds | integer | 固定窗口长度 |
| limit_count | integer | 该窗口配额 |
| window_started_at / window_ends_at | timestamptz | 按 UTC Unix epoch 对齐的固定窗口边界，结束时间由长度确定 |
| request_count | integer | 默认 0；包含被拒绝请求 |
| blocked_until | timestamptz | 超限时为窗口结束时间；与 `request_count > limit_count` 成对，用于计算最长 `Retry-After` |
| created_at / updated_at | timestamptz | NOT NULL |

验证码窗口配额保持：EMAIL `60s/1`、`1h/5`、`24h/10`；IP `10m/20`、`24h/100`；DEVICE `1h/10`、`24h/30`。登录窗口配额固定为：IP `LOGIN_IP_10M=600s/30`、`LOGIN_IP_24H=86400s/300`；EMAIL `LOGIN_EMAIL_15M=900s/10`、`LOGIN_EMAIL_24H=86400s/50`。唯一键覆盖 action、purpose、dimension、主体摘要、密钥版本、策略、窗口标识和窗口开始时间，支持同一主体多时间窗。V010 用显式命名约束锁定 action/purpose/policy/dimension/window/秒数/配额配对；窗口对齐、blocked 状态、唯一键、索引和 7 天删除保护沿用 V008。

主体摘要必须按安全操作、用途、限流维度和规范化主体做域分离 HMAC-SHA-256；验证码与登录分别使用独立域，登录域为 `ziji-auth-login-rate-limit-v1`。HMAC 密钥来自外部密钥配置，不进入数据库、仓库或日志。来源 IP 默认取连接对端，仅在显式受信反向代理配置下接受代理覆盖后的地址；IPv4/IPv6 使用规范二进制地址，IPv4 映射 IPv6 归一为 IPv4。设备缺失时仅验证码发送以来源 IP 和 `MISSING_DEVICE` 域标记生成设备摘要；密码登录不使用 deviceId。

### 3.3 user_sessions

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | PK，设备会话 ID |
| user_id | uuid | FK users |
| device_id | varchar(200) | NULL 或保留客户端原值的 1～200 字符不透明稳定标识，不做 NFKC/trim，且不得全空白 |
| device_name | varchar(200) | 经 NFKC、trim 的 1～100 字符展示名称 |
| issued_at | timestamptz | NOT NULL |
| expires_at | timestamptz | NOT NULL |
| revoked_at | timestamptz | NULL |
| revoke_reason | varchar(50) | NULL |
| last_seen_at | timestamptz | NOT NULL |
| security_baseline_version | smallint | NULL 仅为 V011 前历史行；V011 后 INSERT 由触发器写入 1 |

索引：

- `idx_sessions_user_active(user_id, expires_at) where revoked_at is null`
- `UNIQUE(user_id, device_id) WHERE revoked_at is null`

`user_sessions.id` 是稳定设备会话 ID，刷新 Token 轮换不创建新的 session。V011 对后续写入固定 `expires_at = issued_at + 30 days`，`last_seen_at` 必须处于该绝对窗口内且只可单调更新；创建和成功刷新才可更新 `last_seen_at`。`revoked_at` 与 `revoke_reason` 必须成对，原因仅为 `REPLACED_BY_LOGIN`、`CURRENT_DEVICE`、`SELECTED_DEVICE`、`ALL_DEVICES`、`PASSWORD_RESET`、`REFRESH_TOKEN_REUSE`、`SESSION_EXPIRED`、`SECURITY_ADMIN`。V011 前历史行的 `security_baseline_version` 保持 NULL，不伪造撤销原因或期限；触发器仅允许这类行执行不可逆撤销，禁止借安全状态更新改写 user、设备、期限或 lastSeen 事实。V011 后 INSERT 自动标记为 1 并严格执行全部新约束。

同一用户和同一非空 `device_id` 只能有一个未撤销活动会话；再次登录在同一事务以 `REPLACED_BY_LOGIN` 撤销旧会话及刷新 Token后创建新会话。缺失 `device_id` 时每次登录创建独立会话。

### 3.4 session_refresh_tokens

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | PK |
| session_id | uuid | FK user_sessions |
| token_hash | varchar | UNIQUE，固定 `v1:` + 64 位小写十六进制域分离 SHA-256 摘要，不保存原文 Token |
| issued_at / expires_at | timestamptz | NOT NULL |
| consumed_at | timestamptz | NULL，轮换成功后记录 |
| revoked_at | timestamptz | NULL |
| replaced_by_id | uuid | 自关联，下一枚 Token |
| created_at | timestamptz | NOT NULL |
| security_baseline_version | smallint | NULL 仅为 V011 前历史 Token；V011 后 INSERT 由触发器写入 1 |

Refresh Token 原文固定为 `rt1_` 加 32 字节 SecureRandom 的无填充 Base64URL，只返回客户端一次。V011 新 Token 固定 `created_at = issued_at < expires_at`，Token 到期时间必须与所属 V011 稳定会话完全一致，签发时间位于会话窗口内；replacement 不得自引用且必须同会话并晚于旧 Token 消费。约束触发器延迟到提交，以支持“消费旧 Token → 新建 Token → 关联 replacement”的原子顺序。历史 Token 的 `security_baseline_version` 保持 NULL，且只能消费、撤销或建立已消费后的 replacement，不能通过安全处置改写 token_hash、session、签发/到期或创建时间。已消费 Token 保留可识别状态，后续重用攻击由专门会话撤销用例处理，不得静默当作未知 Token。

同一 session 最多一个尚未消费、未撤销且未过期的当前刷新 Token，由应用事务和部分唯一策略保护。应用角色无 `user_sessions`、`session_refresh_tokens` 的 DELETE 权限，避免删除安全历史规避重用检测。

### 5.1 account_members

| 字段 | 类型 | 说明 |
| --- | --- | --- |

### 5.3 account_inclusion_settings

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | PK |
| membership_id | uuid | FK account_members |
| included | boolean | NOT NULL |
| ratio | numeric(9,6) | NOT NULL，0..1 |
| valid_from | timestamptz | NOT NULL |
| valid_to | timestamptz | NULL |
| created_by | uuid | 必须等于 user_id |
| created_at | timestamptz | NOT NULL |

使用 PostgreSQL range exclusion constraint 防止同一 `membership_id` 的有效时间区间重叠：

```text
EXCLUDE USING gist (
  membership_id WITH =,
  tstzrange(valid_from, valid_to, '[)') WITH &&
)
```

需要启用 `btree_gist` 扩展。当前有效记录使用部分唯一索引保证每个 membership 最多一个 `valid_to is null`。成员周期结束时关闭当前区间；再次加入产生新的 membership 和新的默认设置。

`included=false` 时 `ratio` 必须为 0；`included=true` 允许 `ratio=0`，用于新成员加入后“已启用但暂不计入”的 V1 默认状态。

所有账户创建必须在一个事务中写入 Account、创建者的 ACTIVE OWNER membership、其 100% 计入设置以及账户 LedgerAccount。`accounts.created_by` 不参与权限查询。

## 6. 账务核心

### 6.1 ledger_accounts

| 字段 | 类型 | 说明 |

| id | uuid | PK |

## 12. 幂等与同步

### 12.1 idempotency_records

所有需要 `Idempotency-Key` 的 API 写操作统一使用此表，不能由各业务表自行定义不一致作用域。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | 已认证主体，FK users；与匿名主体二选一 |
| anonymous_subject_hash | bytea | 公开写接口匿名主体的 HMAC-SHA-256 32 字节摘要，不保存原始邮箱 |
| anonymous_subject_hash_key_version | smallint | 匿名主体 HMAC 密钥版本；仅匿名主体存在时为正数 |
| api_major_version | smallint | V1 固定为 1 |
| operation_id | varchar(100) | 稳定 OpenAPI operationId，即接口语义 |
| idempotency_key | varchar(100) | 客户端提供 |
| request_hash | char(64) | 规范化 HTTP 方法、实际资源标识、业务前置条件和载荷的 SHA-256 小写十六进制 |
| status | varchar(16) | PROCESSING/SUCCEEDED/FAILED_RETRYABLE/FAILED_FINAL |
| processing_started_at / processing_lease_expires_at | timestamptz | PROCESSING 30 秒恢复租约；正常路径不单独提交 PROCESSING |
| retry_after_at | timestamptz | FAILED_RETRYABLE 可被同 Key/Hash 接管的最早时间，固定为 completed_at + 5 秒 |
| response_status | smallint | PROCESSING 为 NULL；SUCCEEDED 为 2xx；FAILED_FINAL 为 4xx；FAILED_RETRYABLE 为 5xx |
| response_reference | jsonb | 最多 8 KiB 的安全重放引用，不保存完整敏感响应 |
| resource_type / resource_id | varchar/uuid | 可选业务结果 |
| created_at / completed_at / expires_at | timestamptz | completed 可空 |

V009 以互斥约束保证已认证记录仅有 `user_id`，公开记录仅有长度为 32 的匿名摘要和密钥版本；不能用可空 `user_id` 形成所有匿名请求共享的 NULL 作用域。认证和匿名主体分别使用部分唯一索引：

```text
(user_id, api_major_version, operation_id, idempotency_key) WHERE user_id IS NOT NULL
(anonymous_subject_hash, anonymous_subject_hash_key_version, api_major_version, operation_id, idempotency_key)
  WHERE anonymous_subject_hash IS NOT NULL
```

匿名摘要为 `HMAC-SHA-256(K_idempotency, frame("ZIJI-IDEMPOTENCY-ANONYMOUS-EMAIL-V1", normalizedEmail))`；每段 UTF-8 字节均以前置 4 字节大端长度编码，邮箱沿用认证基线的 NFKC、trim、`Locale.ROOT` 小写。密钥仅由外部配置/密钥管理系统提供，和验证码限流密钥分离；轮换期同时查询当前及上一版本，上一版本至少保留完整的 7 天重放保护期。新建记录只写当前版本，切换版本前须通过实例排空或流量围栏停止旧配置写入。

同作用域相同 Key、相同 request_hash 返回首次安全结果；相同 Key、不同 request_hash 返回 `IDEMPOTENCY_KEY_REUSED`。请求 Hash 的完整规范化见 API§2.4：API 主版本和 operationId 已在作用域中，不在 Hash 中重复；实际资源标识、业务 query、If-Match 和类型化载荷必须参与，不能把任意看似数字的普通字符串改写。

生命周期约束如下：

- `PROCESSING` 不能有结果、资源或重放引用，必须有严格 30 秒租约；它只用于同一事务内的暂态和异常恢复。
- `SUCCEEDED` 必须有 2xx 和安全 `RESOURCE`/`EMPTY` 引用；`FAILED_FINAL` 必须有稳定 4xx 和仅含错误码的 `PROBLEM`；`FAILED_RETRYABLE` 必须有 5xx、错误码和固定 `retryAfterSeconds=5`。
- `response_reference` 只允许 `kind`、相对 `location`、`etag`、`resourceVersion`、`errorCode`、`retryAfterSeconds`，并限制 JSON 字节长度；不得保存 SQL、堆栈、密码、验证码、Token 或完整敏感载荷。

V001 已在共享环境执行，生命周期和安全引用约束以 `NOT VALID` 追加，避免为历史记录伪造响应或改变既有事实；PostgreSQL 仍对 V009 后的 INSERT/UPDATE 强制执行。升级评审必须盘点历史幂等行，未补齐安全终态的历史行不得被普通幂等服务更新或重放。

V1 最大客户端重试窗口为 24 小时，`expires_at` 是最短 7 天重放保护期后的最早清理候选时间，不是业务事实失效时间。到期后仅终态、未被 `transactions` 或 `sync_operations` 外键引用的记录可由后续清理任务删除；已被引用的记录继续保留，绝不级联删除业务事实。清理触发器拒绝未到期或 `PROCESSING` 记录，并显式检查两类业务外键。`idx_idempotency_processing_lease` 与 `idx_idempotency_cleanup_candidate` 支持恢复和安全清理；`ziji_app` 仅在触发器和外键约束下获得该表的 DELETE 权限，PUBLIC 无权访问。

幂等记录、业务写入、审计和 outbox 必须在同一事务完成。请求格式/头校验、认证、CSRF、权限/不可见资源和限流失败不创建记录；同 Key 异 Hash、处理中和锁等待超时也不改写原记录。稳定版本冲突和业务规则错误进入 `FAILED_FINAL` 并重放首次安全错误；只要没有业务事实/outbox 写入的暂时性外部失败可进入 `FAILED_RETRYABLE`，到期后由同 Key/Hash 串行接管。数据库事务回滚时幂等记录一并回滚，不能留下孤儿 PROCESSING。

## 15. 对象存储

数据库只保存对象键和元数据，不保存大文件内容。

导入文件：

- 使用随机对象键，不包含用户邮箱或原始文件名
- 默认私有访问
- 上传和下载使用短时签名 URL 或后端流式代理
- 完成导入后按数据保留策略删除原文件
- 数据库保留摘要、批次结果和审计记录

## 16. 删除、注销和保留

- Transaction、LedgerEntry、Trade、AuditLog 不通过普通业务接口物理删除
- 用户注销先进入 CLOSING 状态，撤销会话并停止新写入
- 共享账户中的共同账务保留，注销用户身份按政策去标识化
- 私有未共享数据在导出和冷静期结束后按政策清理
- 具体保留期限必须由运营主体和合规评审确定
- 幂等记录的 24 小时客户端重试窗口与最短 7 天重放保护期是 V1 已冻结的工程策略，不替代审计、账务或法定保留期；到期且无业务外键的记录才是清理候选
- `transactions`、`sync_operations` 引用的幂等记录不得删除；其审计保留由 `audit_logs` 和业务事实承担，后续若需去标识化或更长保留必须通过新迁移和合规决策，不得级联删除

## 17. 事务边界

以下操作必须在单个数据库事务内完成：

- 创建交易、分录、结构化明细、审计和 outbox
- 创建账户、创建者 OWNER membership、100% 计入设置和账户科目
- 修改交易所需的冲正和新版本
- 投资 Trade、现金分录和 outbox
- 导入单行确认入账；批次状态按行结果独立汇总
- 成员角色转让和“至少一名 OWNER”校验
- 成员退出/移除、关闭该 membership 当前计入区间和定向 ACCESS_REVOKED
- 计入设置关闭同一 membership 的旧区间并创建新区间
- 同步操作结果与业务写入
- 幂等记录的取得/终态、交易或其他业务事实、审计和 outbox；不得先提交 PROCESSING 再在另一事务提交业务事实

导入整批不要求单个超大数据库事务，以免 10,000 行锁表；每行或受控小批次原子写入，批次撤销通过可重试冲正完成。

## 19. 分区策略

V1 标准规模不预先分区，避免增加迁移和唯一约束复杂度。

当满足以下任一指标再评估按业务日期范围分区：

- ledger_entries 超过数千万行
- audit_logs 保留导致单表维护明显受限
- change_log 清理和增量查询出现持续性能问题

分区属于后续数据库 ADR，不应在无数据证据时提前实施。

## 20. 迁移顺序

建议 Flyway 顺序：

1. 扩展、用户和认证。
2. 账户、成员和计入设置。
3. 账务科目、交易和分录。
4. 分类、标签和导入。
5. 金融产品、交易、价格和汇率。
6. 投影、同步、周期账单、outbox 和审计。
7. 约束触发器、权限和初始系统科目/分类数据。
8. 认证挑战失效、固定窗口限流桶和敏感投递边界（V008）。
9. 已认证/匿名幂等主体、请求重放生命周期、最短保护期和安全清理边界（V009）。

每个迁移必须可在空库执行，并在升级测试中从上一发布版本演练。

## 21. 数据库验收门禁

1. 任何非平衡交易无法进入 POSTED 状态。
2. 已 POSTED 分录无法被普通应用角色 UPDATE/DELETE。
3. 幂等记录按认证用户或版本化匿名主体、API 主版本、operationId 和 Key 唯一；同作用域同键异参由 request_hash 拒绝。
4. 外部流水、行情修订和周期发生项不会重复；历史价格、汇率和报表修订不覆盖旧版本。
5. 同一账户和用户允许多个历史 membership 周期，但最多一个 ACTIVE；历史计入设置不存在重叠区间。
6. 余额、流动性占用、持仓、投资收益日历和 Dashboard 投影可从事实表重建且差异为 0。
7. 删除用户或成员不会级联删除共享账务和审计事实。
8. 关键查询在标准数据规模下达到性能验收目标。
9. V008 的认证挑战失效、固定窗口限流桶、HMAC 摘要边界和 7 天清理保留策略满足对应约束。
10. V009 的认证/匿名主体互斥、32 字节摘要、PROCESSING/终态字段、安全 response_reference、最短保留和被业务外键引用的清理边界满足对应约束。
