## 一、结论

**不通过。**

一句话理由：账务与金额主干（复式入账、逐币种平衡、权限、幂等、费用化、THS 限流降级）实现是扎实的，但存在两处阻塞级缺陷 —— 投资成交**没有任何修订/作废路径**，§4.2-3 的"原交易+冲正+新交易"事实链在 B3 无从成立也无法验证；以及被当作 R3 边界证据的 QA-INV-002"持仓投影重建"测试**建立在生产代码从不读写的死表 `position_snapshots` 上，断言恒真、零信息量** —— 另有历史时区归属、缺价静默返回不完整值、明文 HTTP 外部调用、HTTP 层零真实边界测试等 7 项重要问题。

## 三、发现的问题（按严重度）

### 阻塞

**1. 投资成交没有修订/作废路径，§4.2-3 的事实链在 B3 无从成立且不可验证**

- 证据：`TransactionRevisionDetails.java:7-13`（sealed permits 七个分支，无 Investment）；`TransactionCommandController.java:1019-1035`（`revisionDetails()` 无 Investment）；`LedgerCommandApplicationService.java:968-979`（`buildRevision` 无 `INVESTMENT` case）；`investment`/`marketdata` 包无 PATCH/PUT/DELETE 端点。
- 为什么是问题：PRD §8.7/§8.8 把"投资交易生成"列为流水来源之一，§4.2-3 是不可破坏约束。当前一笔买入录错（数量、价格、标的填反）后**没有任何受控修正手段**：用户只能再建一笔反向成交手工对冲，而这笔反向成交会被 `PositionCalculator` 当作真实卖出，释放平均成本并计入已实现收益 —— 等于用新的错误账务事实掩盖旧的错误账务事实，污染持仓成本链、已实现收益与 XIRR 现金流。领域文档 §11.3 已经写好了正确规则（"父交易为 REVERSED/SUPERSEDED 的原 Trade 不参与持仓重建；对应冲正 Transaction 只冲正金额分录，不创建会被误认为正常买卖的 Trade"），说明设计意图是有的，但实现缺失。
- 建议：补 Investment 修订/作废语义（冲正 Transaction 不写 `trades`，原 Trade 因父交易状态迁移被 `PostgresInvestmentFactStore.java:39` 的 `t.status='POSTED'` 自动排除），并在真实 PostgreSQL 下验证"冲正后 POSITION_COST 归零、持仓归零、余额归零、已实现收益回退"。若产品决定 V1 不支持投资成交修正，必须在 PRD/RTM/BOARD 显式登记为范围外并给出替代流程与用户提示，不能默认沉默。

**2. QA-INV-002「持仓投影删除后重建」的边界证据是空转 —— `position_snapshots` 是死表**

- 证据：表建于 `V005__investments_prices_and_exchange_rates.sql:89`；`grep -rn "position_snapshots" backend/src/main/java` **零命中**（生产代码既不写也不读）；持仓读取走 `InvestmentApplicationService.java:610-612` `positions.rebuild(facts.listTrades(...))` 实时重建。`InvestmentPositionProjectionRebuildPostgresIntegrationTests.java:79-90` 先 INSERT 一行伪造投影（`quantity=999999, cost_basis=1`），断言读取结果不变，再 `DELETE` 全部行，再断言结果不变。
- 为什么是问题：因为读取路径根本不看这张表，两条断言**恒真**，无论投影被污染还是被删除都会通过。它目前被 `doc/B3验收收口核对.md:59`（"QA-INV-002 … 既存金标准 2/2、属性 3/3、持仓重建 1/1"）和 `doc/测试与验收方案.md §10.4` 当作"投影可重建"的 R3 边界证据，实际提供的信息量为零，并且会让人误以为持仓存在物化投影、误以为该不变量已被守护。
- 建议：把该测试改为验证真实存在的投影（收益日历快照已有同等有效测试：`InvestmentReturnCalendarRevisionPostgresIntegrationTests.java:199-257` 删除后 31 天逐字段比对，这才是合格写法），或直接把 `position_snapshots` 的作废状态写进 schema 注释/新增迁移标注并同步 `doc/数据库设计.md:640`。无论如何，不得再把它计入 B3 边界证据。

### 重要

**3. 收益日历/持仓估值按「用户当前时区」切历史日界，违反 §4.2-7**

- 证据：`InvestmentApplicationService.java:165`（`listPositions`）、`:262`（`returnCalendar`）、`:313`（`returnDayDetails`）均取 `timezones.currentTimezone(userId)`；`:374-376` `start/end/previousEnd = day.atStartOfDay(zone).toInstant()`；`:616-618` `price()` 用 `asOf.atZone(zone).toLocalDate()` 选业务日。入账侧却是固化的：`:136` 把 `command.timezone()` 存进 transaction，`PostgresLedgerAccountStore.java:32` 用 `AT TIME ZONE t.timezone`（交易行自带时区）。
- 为什么是问题：用户改时区后，同一个 `asOf` 与同一个 `businessDate` 的日界整体平移，历史日/月归属与已入账的 `business_date` 不再一致 —— 正是 §4.2-7 禁止的情形。收益日历按 `YearMonth` 重算时还会得到与旧 revision 不同的日集合，破坏"旧 revision 可审计"的前提。
- 建议：读取侧改用被读事实自身的固化时区（交易行/价格快照时区），或取用户在历史时点的时区快照；至少在 `price()` 与 `calculateDay()` 不再依赖运行时当前时区。补一条"改时区前后同一月份日历逐字段一致"的回归。

**4. 缺价/缺汇率时 `performance()` 静默返回不完整的累计收益，且无任何状态标记**

- 证据：`InvestmentApplicationService.java:184-186`（`unpriced` 为 true 时**全部**市值都不计入 terminalValue，含可估值标的）、`:193-195`（不加期末现金流）、`:196-197`（`xirrStatus = INVALID_CASH_FLOWS`）、`:199-200`（`cumulative` 照常算）、`:586-589`（缺价标的直接 `continue` 跳过 unrealized）。`InvestmentPerformanceResult.java:8-19` 无 unpriced/stale 字段；`InvestmentController.java:352-356` HTTP 也不输出任何提示。
- 为什么是问题：违反 §4.2-11。缺价不是按 0 处理，但按"只算能算的部分"且不明示，调用方无法区分完整值与部分值；更糟的是 `xirrStatus` 被写成 `INVALID_CASH_FLOWS`，把"缺价格"误导成"现金流非法"。同一份代码里收益日历（`:502-511`）已经正确区分 PARTIAL/UNPRICED 并把金额置 null，两侧语义不一致。
- 建议：给 `InvestmentPerformanceResult` 增加 `valuationStatus`/`unpricedInstrumentCount`，缺价时把 `cumulativeProfit`/`returnRate`/`annualizedReturn` 置 null 并把状态置为 PARTIAL/UNPRICED，与日历语义对齐；`xirrStatus` 在缺价场景下不应复用 `INVALID_CASH_FLOWS`。

**5. 同花顺端点使用明文 HTTP，与 SEC-001「全部外部通信使用 HTTPS」冲突**

- 证据：`ThsMarketDataAdapter.java:35` `http://d.10jqka.com.cn/v6/line/hs_%s/01/last1800.js`、`:36` `http://fund.10jqka.com.cn/%s/json/jsondwjz.json`。`doc/需求追踪矩阵.md:225` SEC-001 记为"已验收"。
- 为什么是问题：价格是估值与收益计算的输入事实，明文链路可被中间人篡改（无凭据不等于无风险，`raw_payload_hash` 只保证记录可追溯，不保证来源不可篡改）。这是 CHG-MD-001 引入的新外部依赖，未回到安全基线复核。
- 建议：先验证两个端点是否支持 https，支持则直接改；不支持则在 `doc/同花顺数据源合规评估.md` 与安全台账登记例外 + 缓解措施（如价格合理性校验/多源交叉），并把 SEC-001 的验收范围写明。

**6. 投资 HTTP 层零真实边界测试：幂等、权限、并发、失败原子性全部只覆盖 application 直调**

- 证据：全仓没有 `InvestmentHttpIntegrationTests`；`InvestmentTradeIdempotencyPostgresIntegrationTests.java:126-137` 的 `performTrade` 直接调 `UnifiedIdempotencyService.executeAuthenticated`，复制了 Controller 的 hash 构造，**绕过了 `InvestmentController.createInvestmentTrade`（`InvestmentController.java:100-127`）**，因此 `KEY_REUSED→409`、`REQUEST_IN_PROGRESS→409`、`SAFE_REPLAY_UNAVAILABLE→500`、以及 `:113-119` 的"重放时按 resourceId 从 listTrades 重建响应"分支完全未覆盖；`InvestmentMvcTests.java:80-88` 两个用例用 `mock(InvestmentApplicationService.class)`，仅验证参数校验与字段映射；权限测试无 401/403 HTTP 断言；唯一触及 HTTP 的是 `DashboardHttpIntegrationTests.java:204`，只断言 201。
- 为什么是问题：§4.3 的幂等与授权本质是 HTTP 语义（Key 头、409、403），application 层通过不等于契约成立。重放路径 `:113-119` 里 `listTrades(...).filter(id equals).findFirst().orElseThrow` 是一条会抛 404 的真实分支，零覆盖。

**9. 部分卖出的账面释放成本与领域平均成本不同源，POSITION_COST 会产生分位漂移**

- 证据：`InvestmentApplicationService.java:125` `sellCostBasis = round(current.sell(q).releasedCost(), currency)` —— 舍入到币种精度（CNY 2 位）后入账；而 `Position.java:44-45` 的 `releasedCost` 是 `sellQuantity × averageCost`，`averageCost` 由 `divide(…, 24, HALF_UP)`（`:33,:49`）得到，是 24 位小数。`Position.java:47` 的剩余成本用**未舍入**的 24 位值相减。
- 为什么是问题：每次部分卖出，账面 POSITION_COST 贷方（2 位）与领域剩余成本（24 位基准）就差最多 0.005，多次部分卖出可累积。全卖时 `releasedCost = costBasis`（本身是 2 位的 grossAmount 累加）所以归零，`InvestmentConcurrencyPostgresIntegrationTests.java:124` 只覆盖了这个安全场景。结果是"持仓投影可从事实重建"这条不变量在部分卖出序列下不严格成立。
- 建议：统一释放成本的精度策略（例如账面也按同一 24 位中间值计算后，只在入账分录处做一次 HALF_UP，并把舍入差额显式计入已实现收益/损失科目），并补一条"5 次部分卖出后 POSITION_COST 余额 == 领域 costBasis"的回归断言。
