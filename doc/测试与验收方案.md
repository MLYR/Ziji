# 资迹 Ziji — 测试与验收方案

**文档版本：** V0.1  
**对应产品版本：** V0.1  
**需求基线：** PRD V0.1、RTM V0.1  
**文档状态：** V1 正式测试基线

## 1. 测试目标

V1 测试以财务正确性、数据安全性和跨端一致性为首要目标，不以页面“能打开”作为完成标准。

必须证明：

1. 账户余额、持仓、收益和 Dashboard 可以由事实数据一致重建。
2. 重复提交、离线重试和并发操作不会造成重复或静默覆盖。
3. 用户无法访问未授权账户和共享资源。
4. Tushare、汇率、邮件和文件解析失败时系统能够明确降级。
5. 全部 RTM V1 需求都有测试证据，并达到发布门禁。

## 2. 测试范围

### 2.1 V1 范围内

- 邮箱验证码注册、邮箱密码登录、密码重置和设备会话
- 账户、共享成员、计入比例和历史生效规则
- 收入、支出、退款、转账、负债、冲正和余额调整
- 分类、标签和账单导入
- 股票、基金、ETF、Tushare 数据、持仓和收益
- Dashboard、统计、多币种和汇率
- 移动端离线和多端同步
- 周期账单、安全、导出、注销和备份恢复
- Web、iOS、Android 的 V1 核心流程

### 2.2 V1 范围外

- 财务目标
- 分类预算、灵活预算、预算结转和未来支出预测
- 微信、手机号登录
- 房产、汽车等实物资产
- 银行、支付或证券账户 API 自动同步
- 复杂分期、最低还款和罚息自动计算
- 盘中实时行情

范围外能力不作为 V1 阻塞项，也不得通过未完成占位页面宣称已经支持。

## 3. 测试策略

### 3.1 测试层级

| 层级 | 目标 | 主要对象 | 执行时机 |
| --- | --- | --- | --- |
| 静态检查 | 发现类型、规范和契约问题 | Java、TypeScript、OpenAPI、迁移 | 每次变更 |
| 单元测试 | 验证纯领域规则和计算 | 账务、成本、收益、汇率、权限策略 | 每次变更 |
| 属性测试 | 验证大量组合下不变量 | 借贷平衡、冲正、幂等、成本重建 | 每次变更/夜间 |
| 数据库集成测试 | 验证约束、事务和查询 | PostgreSQL、jOOQ、Flyway | 每次后端变更 |
| API 契约测试 | 验证实现与 OpenAPI 一致 | 请求、响应、错误、权限 | 每次 API 变更 |
| 模块集成测试 | 验证模块协作 | 导入→账务、投资→账务、同步→领域 | 每次相关变更 |
| 端到端测试 | 验证用户完整流程 | Web、iOS、Android | 每个业务闭环/发布前 |
| 专项测试 | 性能、安全、恢复、兼容 | 完整环境 | 里程碑/发布前 |

测试比例不按固定数字追求覆盖率。财务计算和权限分支要求接近完整的规则覆盖，普通展示代码以关键行为覆盖为主。

### 3.2 测试环境

| 环境 | 用途 | 数据要求 |
| --- | --- | --- |
| unit | 纯内存领域测试 | 固定样例、无外部服务 |
| integration | PostgreSQL 集成测试 | 每套测试隔离 schema 或容器 |
| contract | OpenAPI 与服务实现 | 固定契约样例 |
| staging | 端到端、性能、安全和恢复演练 | 合成数据，不使用真实个人财务数据 |

Tushare、邮件和汇率服务在自动化测试中默认使用可控模拟适配器。少量真实供应商冒烟测试只在隔离环境运行，凭据来自密钥设施。

### 3.3 测试框架职责

| 框架 | 固定职责 | 不替代 |
| --- | --- | --- |
| JUnit | Java 领域单元、属性、Spring Modulith 模块边界和后端集成测试入口 | 真实 PostgreSQL 行为验证 |
| Testcontainers | 启动与生产主版本一致的 PostgreSQL 等依赖，验证 Flyway、jOOQ、事务和数据库约束 | 纯领域单元测试 |
| Vitest | Web 组件、状态、工具函数及可脱离原生运行环境的共享 TypeScript 逻辑 | 浏览器或原生端完整流程 |
| Playwright | Web 浏览器端到端、路由、表单、上传、响应式和键盘操作 | iOS/Android 原生流程 |
| Maestro | iOS/Android 核心端到端、离线恢复、系统权限和跨页面流程 | 后端财务不变量验证 |

服务端接口以正式 OpenAPI 为契约；Web 和移动端测试使用 openapi-typescript 生成的同源类型。测试不得维护另一套手写 API 类型来掩盖契约漂移。

## 4. 测试数据原则

- 自动化测试不得使用用户真实邮箱、Token、账单或持仓数据
- 测试数据必须覆盖正数、零值边界、小数、超大值和不同币种
- 固定测试时钟和用户时区，避免依赖运行机器当前时间
- 为行情和汇率固定业务日期，禁止测试依赖当日真实价格
- 密码、验证码和 Token 使用测试替代值，不输出到日志
- 性能数据由生成器创建，并保存生成参数和随机种子

标准性能用户数据：

```text
100 个账户
100,000 条流水
1,000 个持仓价格快照
10,000 行单个导入文件
```

### 5.4 属性测试

使用随机合法交易序列验证：

- 任意已提交交易的每币种借贷和恒等
- 交易加其冲正后，原分录和冲正分录都保留并参与汇总，余额和统计恢复到操作前
- 同一幂等作用域、相同键和相同请求 Hash 重复 N 次只产生一次结果
- 同一幂等作用域复用相同键但请求 Hash 不同时返回 `IDEMPOTENCY_KEY_REUSED`
- 从全部有效 Trade 重算的持仓与投影一致
- 从交易、价格、汇率和历史计入设置重算的全部投资/单一标的日收益与收益日历投影一致
- 卖出不导致负持仓
- 调整计入比例不改变历史生效时间前的统计
- 修改基准币种不改变原币分录

属性测试失败必须保存随机种子和最小反例。

### 7.3 投资收益日历

收益日历测试至少覆盖：

- 全部投资与单一标的两个范围，单一标的跨多个投资账户合并
- 月初买入、月中加仓、部分卖出、清仓、分红、手续费和税费
- 普通账户向投资账户转入/转出不形成组合收益，内部买卖本金不形成收益
- CNY、USD、HKD 持仓使用各日有效汇率，汇率变化进入收益且不进入普通收支
- 股票/ETF 休市、基金净值延迟公布、真实 0 收益、无持仓、缺价格和缺汇率
- 日收益率 Modified Dietz 现金流日内权重，以及分母小于等于 0 时收益率为 null
- 完整月份的月收益等于日收益之和、月收益率等于完整每日收益率几何链接
- 任一应计算日为 PENDING_DATA/PARTIAL/UNPRICED 时月度汇总不得伪装为完整值
- 历史交易、价格、净值、汇率或计入设置修正后生成新 valuationRevision，旧版可审计
- Web 与 Mobile 点击日期后，明细、贡献和日历格数值一致

所有金额以服务端结果为准；客户端测试不得复制收益公式构造“预期实现”。金标准由独立测试数据和高精度参考计算生成。

- 邮件、Tushare 和汇率响应的字段长度、空值、重复和异常数值

- 容器镜像和基础镜像漏洞扫描
- 客户端包中密钥、源映射和调试日志扫描

上线前执行独立安全审查；高危问题必须修复或由责任人书面接受风险。

## 12. 性能和可靠性测试

### 12.1 性能场景

`T-PERF-001` 是以下 V1 性能验收场景的统一测试组，对应需求 OPS-002：

| 用例 ID | 场景 | 数据规模 | 通过标准 |
| --- | --- | --- | --- |
| T-PERF-001-A | Dashboard 查询 | 标准用户 | 服务端 P95 ≤ 2 秒；OPS-002 |
| T-PERF-001-B | 流水游标分页 | 100,000 条流水 | 服务端 P95 ≤ 1 秒；OPS-002 |
| T-PERF-001-C | 账单解析与去重 | 10,000 行 | ≤ 60 秒；OPS-002 |
| T-PERF-001-D | 同步增量拉取 | 200 条/页 | 无遗漏，响应时间纳入 1 秒观察目标；OPS-002 |
| T-PERF-001-E | 持仓和估值查询 | 1,000 个快照 | 满足 Dashboard 总目标；OPS-002 |
| T-PERF-001-F | Web 与移动端进入首页 | 标准用户、无数据异常 | 从发起首页加载到核心指标可见 ≤ 3 秒；超时或失败显示明确状态和重试入口；OPS-002 |

### 12.2 稳定性

- 持续写入和查询 2 小时，无内存持续增长和连接泄漏
- 导入、outbox、行情同步失败后重启可继续处理
- 后端进程在提交前崩溃不留下部分交易
- 后端在提交后响应前崩溃，客户端重试返回幂等结果
- Tushare 持续失败时不形成无界重试队列

| T-OPS-002 | 模拟同步、导入、行情和 outbox 失败 | 指标、日志和告警可定位问题 | OPS-003 |

## 14. RTM 覆盖和缺陷管理

### 14.1 覆盖要求

- 每个 V1 需求至少有一个测试用例 ID
- 高风险需求必须同时有领域单元、数据库/API 集成和端到端证据
- 每个测试用例反向关联需求 ID
- 自动化执行结果保存代码版本、环境和时间
- 手工验收保存操作人、结果和证据链接

### 14.2 缺陷等级

| 等级 | 定义 | 发布处理 |
| --- | --- | --- |
| S0 | 数据丢失、资金计算错误、跨用户泄露、无法恢复 | 必须阻塞发布 |
| S1 | 核心流程不可用、重复入账、静默覆盖、关键权限错误 | 必须阻塞发布 |
| S2 | 有可靠绕行方案的主要功能问题 | 产品负责人决定，默认阻塞 |
| S3 | 非核心体验或轻微展示问题 | 可记录后续修复 |

任何账务差异即使金额很小也不能按普通展示缺陷降级。
