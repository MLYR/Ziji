**产品类型：** 个人资金管理

## 1. 产品概述

### 1.1 产品定位

资迹是一款以 **“我现在有多少钱”** 为核心的个人资金管理工具。

系统统一管理用户分散在不同渠道中的资金，包括：

- 银行卡
- 微信
- 支付宝
- 现金
- 股票
- 基金
- ETF
- 信用卡
- 借款及其他负债

通过账户、流水、投资和负债数据，形成统一的个人资金视图。

产品重点不是传统预算记账，而是：

> 清楚、准确、持续地掌握个人当前资产规模、资产分布和资产变化。

### 1.2 V1 交付原则

本文档内标记为 V1 的能力表示首个正式发布范围；当前项目与需求基线版本为 V0.1。

V1 按实施依赖划分为多个批次，但批次只代表开发和联调顺序，不代表独立发布版本。全部批次完成并通过验收后，V1 才算完成。

## 2. 产品目标

### 2.1 核心目标

用户打开资迹后，可以快速回答：

1. 我现在一共有多少资产？
2. 资产分别在哪里？
3. 有多少资金可以直接使用？
4. 有多少资产正在投资？
5. 当前有多少负债？
6. 当前净资产是多少？
7. 最近资产增加或减少了多少，原因是什么？
8. 投资目前赚了还是亏了？

### 2.2 长期目标

逐步形成类似 Personal Finance Dashboard 的统一个人金融数据平台。

## 4. 核心指标和统计口径

### 4.1 基本原则

所有个人指标均按照以下因素计算：

- 账户是否计入个人统计
- 用户在共享账户中的资产计入比例
- 指标对应时点的账户余额、持仓价格和汇率
- 用户设置的基准币种

负债始终以正数展示，并在计算净资产时扣减。

### 4.2 资产总额

用户当前拥有并选择计入统计的全部资产，包含现金类资产和投资资产。

```text
资产总额 = Σ（普通资产账户余额 × 个人计入比例）
         + Σ（投资账户券商现金余额 × 个人计入比例）
         + Σ（投资持仓市值 × 个人计入比例）
```

不同币种先按指标时点汇率折算为用户基准币种。

### 4.3 可用资金

可以直接使用或短期支配的资金，包括：

- 银行卡可用余额
- 微信余额
- 支付宝余额
- 现金
- 其他可随时支配的资金账户余额

不包含：

- 股票、基金、ETF 等投资资产
- 投资账户中的券商现金余额
- 冻结金额
- 明确标记为不可用或在途的金额
- 未计入个人统计的账户金额

```text
可用资金 = Σ（账户可用余额 × 个人计入比例）
```

### 4.4 投资资产

投资资产按照最新有效市场价格计算：

```text
投资资产 = Σ（投资账户券商现金余额 × 个人计入比例）
         + Σ（持仓数量 × 最新有效价格 × 个人计入比例）
```

价格非基准币种时，需要按最新有效汇率折算。Dashboard 必须展示行情时间；行情超过配置的有效期时必须标记“数据可能已过期”。

### 4.5 负债总额

用户当前需要偿还并选择计入个人统计的全部负债：

```text
负债总额 = Σ（负债账户剩余本金 × 个人计入比例）
```

V1 不自动生成未支付利息或费用的应计负债。只有已经通过正式交易入账的负债金额参与负债总额；“本期应还金额”等提醒字段不是账务余额事实。实际支付利息或费用时再按支出入账。自动计提能力放入后续版本评审。

### 4.6 净资产

```text
净资产 = 资产总额 - 负债总额
```

净资产是产品最核心指标。

### 4.7 资产变化归因

“今日变化”和历史资产变化至少拆分为：

- 收入和支出带来的变化
- 投资价格变化
- 汇率变化
- 余额调整
- 统计范围或共享计入比例变化

跨两个已计入统计的同币种账户进行无手续费转账，不改变资产总额。

以下情况会改变已统计资产，但不应被误记为日常收入或支出：

- 在计入统计和不计入统计的账户之间转账
- 共享账户计入比例变更
- 账户是否计入统计的设置变更
- 汇率变化

## 5. 用户体系

### 5.1 注册和登录

V1 支持：

- 邮箱验证码注册
- 邮箱和密码登录
- 邮箱验证码找回或重置密码
- 退出当前设备
- 退出全部设备
- 修改个人资料
- 修改密码
- 查看并撤销已登录设备

每个设备会话具有稳定 `sessionId`。刷新凭据轮换不会改变设备会话 ID；旧刷新凭据被重复使用时，服务端撤销整个设备会话并要求重新登录。

邮箱地址在同一系统内唯一。注册前必须完成邮箱验证码校验。

V1 不支持微信登录和手机号登录，后续版本再评估接入。

验证码发送安全基线：

- `EmailChallengeRequest` 的 `deviceId` 为可选字符串，长度 1～200；缺失时不拒绝请求，而是以来源 IP 与 `MISSING_DEVICE` 域标记共同生成设备维度摘要，不能通过省略字段绕过设备限流。
- 来源 IP 默认取服务端连接对端；只有部署显式配置受信反向代理且代理覆盖客户端传入的转发头时，才使用代理提供的客户端地址。客户端自行提交的 `Forwarded`/`X-Forwarded-For` 不得影响限流主体。
- 验证码有效期固定为 10 分钟，单个验证码最多允许 5 次错误尝试；新验证码及其投递事件成功写入后，同邮箱、同用途的旧活动验证码立即标记为 `REPLACED`。
- `REGISTER` 与 `RESET_PASSWORD` 的限流分别计算，服务端不得通过响应区分邮箱是否已存在。
- 邮件投递失败不退还限流次数；outbox 重试同一挑战，不重新生成验证码。

密码登录安全基线：

- 所有语法合法的登录请求均由 PostgreSQL 固定窗口计数，包括成功、密码错误、邮箱不存在、`LOCKED`、`CLOSED` 和已超限请求；顺序固定为来源 IP 的 10 分钟、24 小时窗口，再到邮箱的 15 分钟、24 小时窗口。
- 登录配额固定为：来源 IP `10 分钟/30 次`、`24 小时/300 次`；邮箱 `15 分钟/10 次`、`24 小时/50 次`。任一窗口超限返回 `429 RATE_LIMITED`，`Retry-After` 为所有超限窗口的最长剩余时间；登录不使用 `deviceId` 作为限流维度。
- `ACTIVE`、`CLOSING` 可完成凭据认证；`LOCKED`、`CLOSED`、邮箱不存在和密码错误统一返回 `401 INVALID_CREDENTIALS`，不泄露账号存在、状态、密码版本或内部失败原因。
- 邮箱不存在仍执行一次与生产相同参数的 Argon2id 校验；应用启动时生成并复用一个 dummy Hash，已存在用户无论状态也执行一次校验。密码、Hash 和原始邮箱不得写入日志、异常、审计 metadata 或限流桶。

稳定设备会话与 Token 安全基线：

- 每次成功登录创建新的稳定 `sessionId`；同一用户再次以相同的非空 `deviceId` 登录时，在同一事务撤销旧活动会话及其刷新 Token，原因固定为 `REPLACED_BY_LOGIN`，再创建新会话。`deviceId` 缺失时每次登录创建独立会话；`deviceName` 经 NFKC、trim 后必须为 1～100 字符，`deviceId` 是保留客户端原值的不透明稳定标识，非空时为 1～200 字符且不得全空白，不做 NFKC 或 trim。
- 会话与刷新 Token 均固定 30 天绝对有效期，刷新轮换不延长 `session.expiresAt`、不改变 `sessionId`；创建与成功刷新才更新 `lastSeenAt`。刷新 Token 的 `createdAt` 固定等于 `issuedAt`，轮换后的 Token 仍以原 session.expiresAt 为上限。原文格式为 `rt1_` 加 32 字节 `SecureRandom` 的无填充 Base64URL，客户端只接收一次，数据库只保存 `v1:` 加域分离 SHA-256 的 64 位小写十六进制摘要。
- Access Token 固定使用 RSA 至少 2048 位的 RS256 JWT，含受控 `kid`、`typ=at+jwt`、`iss=ziji-backend`、`aud=ziji-api`、`sub`、`sid`、`jti`、`iat`、`nbf`、`exp`；有效期 30 分钟、时钟偏差最多 60 秒且不得超过会话绝对到期。Access Token 不写数据库、日志、异常、审计 metadata、outbox 或幂等记录。
- 刷新由 PostgreSQL 行锁在一个事务中完成旧 Token 消费、新 Token 插入、`replacedById` 关联和 `lastSeenAt` 更新；同一 Token 并发最多一个正常成功。已消费 Token 必须保留可识别状态，后续重用攻击撤销由专门用例处理，不能静默视为未知 Token。
- 签名私钥及公钥只从部署环境或密钥设施注入；当前私钥签发，当前和上一受信公钥按明确 `kid` 验证，上一公钥停止签发后至少保留 24 小时。测试 RSA 密钥仅可位于 test profile，不能进入 local、staging 或 production。

### 5.2 生物识别

移动端生物识别用于本地解锁应用和保护本地保存的登录凭据，不等同于服务器账号登录方式。

生物识别失败或设备不支持时，用户仍可使用应用密码或重新登录。

### 5.3 用户设置

用户至少可以设置：

- 昵称
- 用户时区
- 基准币种，默认 CNY
- 默认语言和金额展示格式

### 6.2 账户基本信息

账户至少包含：

- 账户名称
- 账户大类和子类型
- 所属机构
- 币种
- 备注
- 是否计入个人统计
- 可用余额或冻结金额，适用时记录
- 账户状态：正常、归档
- 创建时间
- 更新时间
- 数据版本号

“是否计入个人统计”属于用户维度设置。共享账户中，每位成员可以有不同设置。

### 6.3 期初余额

新建已有余额的账户时，用户必须能够录入：

- 期初余额
- 余额对应日期和时间
- 可选备注

系统自动生成一笔“期初余额交易”和相应账务分录。期初余额影响资产，但不计入收入或支出。

### 6.4 当前余额和事实源

`LedgerEntry` 是账户余额的唯一账务事实源。

账户当前余额必须根据有效账务分录计算。系统可以为了性能保存余额缓存或快照，但缓存不是独立事实；缓存与分录不一致时，以分录重算结果为准。

用户不能直接覆盖账户余额。发现实际余额与系统余额不一致时，必须通过“余额调整”功能生成调整交易，并记录：

- 调整前余额
- 实际余额
- 调整差额
- 调整原因
- 操作人和操作时间

余额调整影响资产变化，但默认不计入日常收入或支出统计，并在资产变化归因中单独展示。

### 6.5 可用余额和流动性占用

账户账面余额仍以 `LedgerEntry` 为唯一账务事实。冻结、在途和预留金额属于流动性占用事实，只影响资金是否可以立即使用，不改变资产总额、净资产或收支。

```text
不可用金额 = Σ（当前有效的冻结金额 + 在途金额 + 预留金额）
可用余额 = 账面余额 - 不可用金额
```

流动性占用必须记录类型、金额、币种、生效时间、可选失效时间、来源、备注和操作审计。用户不能直接填写“可用余额”；只能新增、修改或释放流动性占用记录。没有流动性占用记录时，不可用金额为 0，可用余额等于账面余额。

流动性占用类型使用稳定机器枚举 `FROZEN`、`IN_TRANSIT`、`RESERVED`。公共人工操作的来源由服务端固定为 `MANUAL`，客户端不能提交或伪造 `IMPORT`、`SYSTEM`。公共 API 的 `reason` 对应存储备注；修订理由随新版本备注保存并由审计动作表达，不接收无法持久化的独立修订理由字段。

未来生效的占用在生效前不影响可用余额；到达失效时间即逻辑过期，系统必须在查询、释放和修改前按当前时点判断，即使自动过期记录的最终化尚未完成。已释放、已替代和已过期的历史版本保留用于审计和重建，不得再次作为当前可操作版本。

若账户余额后续变化导致不可用金额超过账面余额，系统保留计算出的负可用余额并展示数据质量警告，不得静默截断为 0。

### 6.6 账户归档

已有流水的账户不得物理删除，只能归档。

归档账户默认不出现在日常录入列表中，但历史流水、历史趋势和审计记录必须保留。归档前存在非零余额时，系统必须提醒用户先转出、还清或执行余额调整。

## 7. 共享账户

系统支持一个账户由多个用户共同维护，例如夫妻共同银行卡、家庭公共资金账户和共同投资账户。

所有账户统一使用成员模型，不区分“个人账户表”和“共享账户表”。创建账户时，系统必须在同一事务中为创建者创建 `ACTIVE OWNER` 成员周期，以及 `included=true、ratio=100%` 的个人计入设置。账户创建者字段只用于审计，不替代成员权限。

### 7.1 邀请和成员管理

账户 OWNER 可以通过已注册邮箱邀请其他资迹用户加入账户。

邀请必须具有有效期，并支持接受、拒绝和撤销。重复邀请不得创建重复成员。

成员可以主动退出共享账户，但唯一 OWNER 退出前必须先转让所有权。OWNER 可以移除其他成员；移除只影响后续访问权限，不删除该成员已经产生的审计记录。

成员退出或被移除时，系统关闭该成员周期下当前生效的计入设置。相同用户再次加入同一账户时创建新的成员周期，并按新成员规则创建 `included=true、ratio=0%` 的计入设置，不继承上一次加入的设置。

### 7.2 角色权限

| 操作 | OWNER | EDITOR | VIEWER |
| --- | --- | --- | --- |
| 查看账户、流水和统计 | 是 | 是 | 是 |
| 查看流动性占用及完整修订历史 | 是 | 是 | 是 |
| 新增流水 | 是 | 是 | 否 |
| 修改或作废流水 | 是 | 是 | 否 |
| 创建、修订或释放流动性占用 | 是 | 是 | 否 |
| 管理账户内分类 | 是 | 是 | 否 |
| 修改账户资料和归档账户 | 是 | 否 | 否 |
| 邀请、移除成员和修改角色 | 是 | 否 | 否 |
| 转让 OWNER | 是 | 否 | 否 |
| 修改自己的计入设置和比例 | 是 | 是 | 是 |
| 修改他人的计入设置和比例 | 否 | 否 | 否 |

每个账户至少保留一名 OWNER。

### 7.3 资产计入比例

资产计入比例只影响当前用户自己的 Dashboard 和统计，不改变账户真实余额，也不代表法律意义上的资产所有权。

规则如下：

- 每位成员独立设置 0%～100%
- 系统不要求全部成员比例之和等于 100%
- OWNER 创建账户时默认 100%
- 新加入成员默认 0%
- 每位成员只能修改自己的比例
- 资产计入比例与操作权限相互独立

### 7.4 历史生效规则

资产计入比例和“是否计入个人统计”采用带生效时间的历史记录。

修改只影响生效时间之后的 Dashboard 和统计，不回改此前历史数据。历史报表必须使用对应历史时点实际生效的比例和设置。

## 8. 流水和账务管理

### 8.1 基本原则

`Transaction` 表示一次完整资金事件，`LedgerEntry` 表示该事件产生的账务分录。

核心账务采用简化复式账务模型：

- 一笔交易可以产生多条账务分录
- 同一交易的所有分录必须原子写入或全部失败
- 每个币种内的分录必须借贷平衡
- 收入、支出等单边资金变化由系统管理的收入、支出或权益类对方科目完成平衡
- 已确认分录不可原地覆盖或物理删除

### 8.2 流水类型

- 期初余额
- 收入
- 支出
- 退款
- 转账
- 余额调整
- 投资交易
- 还款
- 利息和费用

### 8.3 收入

收入记录至少包含：

- 金额和币种
- 收款账户
- 分类
- 日期时间
- 对方或付款方
- 备注
- 标签

工资、奖金、利息和分红可以计入收入。账户间转入、投资卖出本金和负债借入不得计入收入。

### 8.4 支出

支出记录至少包含：

- 金额和币种
- 付款账户或负债账户
- 分类
- 日期时间
- 商户
- 标签
- 备注

投资买入本金、账户间转出和偿还负债本金不得计入支出。投资手续费、税费、借款利息及其他实际费用计入支出。

### 8.5 退款

退款应优先关联原支出，并冲减原支出分类的统计金额，不作为普通收入。

无法关联原支出时，可以记录为独立退款，但必须选择被冲减的支出分类并明确标识来源。

### 8.6 转账

转账必须同时记录：

- 转出账户和转出金额
- 转入账户和转入金额
- 币种
- 日期时间
- 手续费，适用时记录
- 汇率，跨币种时记录

同币种、无手续费且转入转出账户均计入当前用户统计时，转账不改变资产总额，也不计入收入和支出。

手续费作为独立费用分录计入支出。

跨币种转账必须分别记录转出金额和转入金额，并保存实际或用户确认的成交汇率。不同币种的分录分别平衡，Dashboard 再按基准币种估值。

### 8.7 修改、作废和冲正

用户界面允许修改或作废流水，但数据库不得物理删除已确认交易和分录。

- 修改已确认交易：保留旧版本，生成冲正分录和新的有效版本
- 作废已确认交易：生成冲正分录并将原交易标记为已作废
- 修改尚未同步的本地交易：可以在本地覆盖，首次同步后遵循上述规则
- 所有修改和作废必须记录操作人、时间、原因和版本关系

### 8.8 流水来源和审计

流水来源包括：

- 手工录入
- 文件导入
- 周期账单生成
- 投资交易生成
- 余额调整生成
- 同步操作

所有流水记录：

- 创建人和创建时间
- 最后修改人和修改时间
- 来源
- 客户端操作 ID
- 数据版本号
- 作废或冲正关系

共享账户中的每次操作都必须验证成员权限并写入审计日志。

Ledger 的初次入账、已确认交易修订和已确认交易作废分别追加稳定的
`TRANSACTION_POSTED`、`TRANSACTION_REVISED`、`TRANSACTION_VOIDED` 审计动作；审计资源类型固定为
`TRANSACTION`，资源标识固定为被操作业务版本链的根交易 ID。初次入账的根交易 ID 等于当前交易 ID；
修订和作废的审计记录必须能以最小脱敏关联信息查到原版本、冲正交易、替代版本（仅修订）、版本号和实体版本。
单账户交易写入该账户 ID，多账户交易或没有唯一可见账户的交易不伪造单一账户，审计 `accountId` 为空。

修订或作废时，原已确认 Transaction 在状态迁移前的持久化版本固定称为
`originalEntityVersionBefore`，等于本次乐观锁预期值；迁移到 `SUPERSEDED` 或 `REVERSED` 后固定称为
`originalEntityVersionAfter`，等于前者加 1。修订替代 Transaction 和冲正 Transaction 已确认写入后的版本分别为
`replacementEntityVersion`、`reversalEntityVersion`。审计 `requestId` 只使用当前受控 HTTP 请求或系统任务的
requestId / correlation ID，不得由 Transaction、root Transaction、outbox、客户端操作、幂等或任意业务资源 ID
代替。

审计只记录已提交的成功事实：用户发起时使用 `USER + actorUserId`，受控系统任务发起时使用
`SYSTEM + null actorUserId`，不以交易 `source` 替代实际操作者。修订的固定 `reasonCode` 为
`SUPERSEDED`，作废的固定 `reasonCode` 为 `REVERSED`，初次入账不填写 `reasonCode`。修改或作废的
原因文本只保存到对应冲正 Transaction 的 `note`；修订后的业务备注仍只保存到替代 Transaction 的
`note`。原因文本、业务备注、完整请求、SQL、Token、密码、Cookie 和幂等键均不得复制到审计 metadata 或
outbox payload。

每个新增的非冲正已确认 Transaction 产生 `TransactionPosted` outbox 事件；每个冲正 Transaction
产生 `TransactionReversed` outbox 事件。初次入账产生前者；修订在同一事务内逻辑上先产生冲正事件、再产生
替代版本的入账事件；作废只产生冲正事件。事件只携带消费方定位和幂等所需的交易 ID、根交易 ID、版本和
关联 ID，不能携带完整 Transaction、分录、金额明细、note/reason 文本、请求体、凭据或 SQL。交易、分录、
审计、outbox 及适用的幂等终态必须在同一最外层数据库事务提交，任一写入失败均不得留下部分事实。

## 9. 分类和标签体系

系统支持收入、支出等不同类型的默认分类和用户自定义分类。

V1 支持两级分类，例如：

- 餐饮：早餐、午餐、晚餐、外卖、聚餐
- 交通：打车、公交、地铁、加油
- 收入：工资、奖金、利息、分红、其他

规则如下：

- 同一分类树中名称不可重复
- 已被流水使用的分类不得物理删除，只能停用或合并
- 分类合并必须保留历史映射
- 标签允许一笔流水设置多个
- 共享账户分类修改遵循账户成员权限

## 10. 账单导入

V1 采用半自动文件接入方式，支持：

- 微信账单
- 支付宝账单
- 银行 CSV
- 银行 Excel
- 通用 CSV

### 10.1 导入流程

```text
文件上传
→ 文件安全校验
→ 识别数据格式
→ 字段映射
→ 数据解析和格式校验
→ 自动分类
→ 重复检测
→ 用户确认
→ 原子写入流水和分录
→ 生成导入结果
```

解析失败的行必须展示具体原因，并允许用户修正映射或排除错误行后继续。

### 10.2 重复检测

重复检测分为两类：

#### 精确重复

来源渠道和账户范围内，外部流水号相同的记录视为精确重复，不允许重复写入。

同一个导入批次或相同文件重复提交时，必须通过文件摘要、外部流水号和导入幂等键避免重复写入。

#### 疑似重复

没有可靠外部流水号时，系统综合以下字段生成相似度判断：

- 金额和币种
- 时间
- 商户或对方
- 账户
- 流水方向

疑似重复只做提示，由用户选择跳过、合并或仍然导入，系统不得仅凭相似字段自动删除现有流水。

### 10.3 导入批次撤销

每次导入生成独立 `ImportBatch`。用户可以在权限允许的情况下整体撤销批次。

撤销通过批量冲正完成，不物理删除流水；已经被后续交易关联的记录必须先提示影响并要求用户确认。

## 11. 投资管理

### 11.1 投资类型

V1 支持：

- 股票
- 基金
- ETF
- 可由用户手工维护的其他证券类资产

### 11.2 金融产品数据源

V1 使用 **Tushare Pro** 作为股票、基金和 ETF 基础信息及行情数据的首选外部来源。

V1 接入范围包括：

- A 股基础信息、上市状态和交易日历
- A 股盘后日线行情
- 场内 ETF 基础信息和盘后日线行情
- 场内、场外公募基金基础信息
- 场外公募基金最新公布的单位净值

不同产品使用不同估值价格：

- A 股使用最新有效的未复权收盘价计算当前持仓市值
- 场内 ETF 使用最新有效的场内收盘价计算当前持仓市值
- 场外基金使用最新公布的单位净值计算当前持仓市值
- 复权数据用于收益分析时单独保存，不得替代真实成交价或当前估值价格

V1 的必要交付标准是盘后日线和最新公布净值，不要求盘中实时行情。若项目已经取得 Tushare Pro 对应实时接口权限，可以在相同数据适配层中扩展实时数据，但实时能力不作为 V1 完成条件。

Tushare Pro 无法覆盖、接口暂时不可用或当前账号无权限的数据，允许用户手工创建金融产品并维护价格或净值。系统不得因为外部数据缺失而阻止用户记录投资交易。

#### 数据接入规则

- 所有 Tushare Pro 调用由服务端统一发起，Web 和移动端不得直接调用
- Tushare Token 作为服务端密钥保存，不得写入客户端、代码仓库或普通日志
- 使用 Tushare `ts_code` 作为外部标识，同时保存系统内部不可变 `instrument_id`
- 数据源字段必须经过适配层转换，不得让 Tushare 字段直接渗透到核心领域模型
- 调用必须遵守当前账户的积分、接口权限、频率和单次数据量限制
- 服务端应按交易日批量同步并缓存数据，避免为每个用户或持仓重复请求相同产品
- 同步任务支持限流、超时、重试和失败告警；重试必须幂等
- 保存外部数据来源、对应业务日期、获取时间和原始更新时间
- 同一产品同一业务日期的数据更新必须采用幂等覆盖或版本记录，不得生成重复价格快照
- 上线前必须确认 Tushare Pro 当前协议、商业使用及数据展示授权；未获得所需授权的数据不得对外提供

Tushare Pro 属于可替换的外部数据源。核心模型和业务接口不得依赖某一供应商实现，以便后续更换或增加数据源。

### 11.3 投资交易

支持：

- 买入
- 卖出
- 分红
- 手续费
- 税费

交易至少记录：

- 投资账户
- 标的及市场
- 数量
- 成交价格和币种
- 成交金额
- 手续费和税费
- 交易日期时间
- 结算现金账户

买入、卖出及其现金变动必须作为同一交易原子记账，避免现金余额和持仓不一致。

投资账户内部的券商现金余额是投资成交的唯一结算现金。买入、卖出和分红只改变该投资账户的券商现金科目；银行卡与投资账户之间的入金或出金使用普通转账单独记录。投资成交接口不允许直接选择任意外部现金账户作为结算账户。

### 11.4 持仓和成本

系统根据有效投资交易自动计算：

- 当前持仓数量
- 持仓成本
- 移动加权平均成本
- 当前价格
- 当前市值

V1 统一采用移动加权平均成本法计算卖出成本和已实现收益。数量必须支持小数，以适配基金份额。

### 11.5 行情

系统通过 Tushare Pro 自动获取行情或净值，并支持用户手工补录和修正。

每条价格必须记录：

- 标的
- 价格和币种
- 价格对应时间
- 数据来源
- 外部数据标识
- 是否由用户手工修正

Dashboard 和投资页面必须展示价格对应日期、获取时间、数据来源及过期状态。自动行情不可用时，用户可以输入价格继续完成资产统计，系统不得将缺失价格静默当作 0。

Tushare Pro 数据和用户手工价格同时存在时，用户手工修正优先，但只覆盖指定产品和业务日期；系统必须保留外部原值、修正值、修正人和修正原因。

### 11.6 投资收益

V1 支持：

- 已实现收益
- 未实现收益
- 累计收益
- 收益率
- 年化收益率
- XIRR

口径如下：

- 已实现收益按移动加权平均成本计算
- 未实现收益按最新有效价格与剩余持仓成本计算
- 分红计入投资收益和收入，并增加对应现金账户余额
- V1 的投资手续费和税费统一作为投资费用计入支出，不进入持仓成本；收益报表按统一口径扣减且不得重复扣减
- XIRR 使用实际发生日期的外部现金流计算，账户内部买卖不重复作为外部现金流

### 11.7 投资分析

支持：

- 投资资产总额
- 股票、基金和 ETF 占比
- 单个持仓占比
- 盈亏排行
- 历史收益曲线
- 行情更新时间和数据来源

“今日盈亏”在 V1 默认表示相邻两个有效交易日收盘价或相邻两个公布净值之间的持仓盈亏变化，不代表盘中实时盈亏。界面必须避免使用“实时”字样误导用户。

### 11.8 投资收益日历

V1 必须提供按自然月查看的投资收益日历，支持以下统计范围：

- **全部投资：** 汇总当前用户在各业务日期实际计入统计的全部投资账户，包括投资账户 `PRIMARY` 券商现金和持仓市值。
- **单一标的：** 汇总当前用户在全部计入统计的投资账户中持有的某一股票、基金或 ETF；同一标的跨账户持有时合并展示。

日历默认使用用户当前基准币种，支持在“收益金额”和“收益率”之间切换。每个日期展示完整日期、计算状态以及可用时的收益金额和收益率；用户选择日期后可以查看当日收益明细。全部投资范围按标的展示当日收益贡献，单一标的范围展示日初/日终市值、净现金流、价格影响、汇率影响、分红、手续费和税费。

全部投资的日收益金额采用投资组合边界口径：

```text
日收益金额 = 日终投资资产 - 日初投资资产 - 当日投资组合净外部现金流
```

投资资产包含券商现金和持仓市值。普通资金账户与投资账户之间的转入为正外部现金流，转出为负外部现金流；投资账户内部买卖、分红到账及券商现金与持仓之间的变化不是组合外部现金流，因此不会把本金移动误算为收益。

单一标的的日收益金额采用标的边界口径：

```text
日收益金额 = 日终持仓市值 - 日初持仓市值 - 当日标的净现金流
```

买入成交金额及其手续费、税费为流入标的的正现金流；卖出净回款和分红为流出标的的负现金流。该口径确保买入本金不是收益，并且手续费和税费只扣减一次。

日收益率使用 Modified Dietz 口径：

```text
日收益率 = 日收益金额 ÷（日初价值 + Σ 当日现金流 × 剩余日内权重）
```

权重根据业务日内现金流时间计算；分母小于或等于 0 时，收益率返回不可用，不得伪造为 0%。自然月汇总只使用已完整计算的日期；存在缺价、缺汇率或待公布净值时必须标记完整性，不能把不完整月度结果当作完整结果。

日期状态必须至少区分：

- `CALCULATED`：已经完整计算，收益可以为正、负或真实的 0
- `NON_TRADING_DAY`：非交易日，不显示成 0
- `NO_POSITION`：当日没有持仓，不显示成 0
- `PENDING_DATA`：尚未收盘、净值待公布或投影正在计算
- `PARTIAL`：组合部分标的缺价格或汇率，完整收益不可用
- `UNPRICED`：统计范围无法估值

日期状态、正负收益和数据质量不能只靠颜色表达。日历及明细必须展示 `valuationRevision`、数据截至时间和必要的数据质量提示。历史价格、净值、汇率或交易被修正后，受影响日期和月份自动生成新修订，默认展示最新结果，旧结果保留用于审计。

### 13.6 总资产变化日历

V1 必须提供按用户时区自然月查看的总资产变化日历。界面名称使用“总资产日历”或“资产变化日历”，不得把它标为“投资收益”：工资、消费、借款到账、还款本金、余额调整和统计范围变化都会改变资产，但不都是投资收益。

日历默认展示 `TOTAL_ASSETS`，并支持切换 `NET_ASSETS`。每个自然日展示当日变化金额，也可以切换为变化率：

```text
当日总资产变化 = 当日日终总资产 - 当日日初总资产
当日净资产变化 = 当日日终净资产 - 当日日初净资产
当日变化率 = 当日变化金额 ÷ 当日日初值
```

日初值等于用户时区下上一自然日日终值。日初值小于或等于 0 时，变化率返回不可用，不得伪造为 0%。周末或休市日不自动视为“无数据”；只要资产估值完整且没有变化，就显示真实的 `CALCULATED + 0.00`。

选择日期后必须展示日初、日终和变化后的总资产、负债与净资产恒等关系，并按账户余额/交易、投资价格、汇率、余额调整和计入范围变化下钻。收入、支出、借款本金、还款本金等需要保留各自语义；两个均计入统计的账户之间转账对总资产和净资产的贡献为 0，不得重复计算为增加或减少。

日期状态固定区分：

- `CALCULATED`：完整计算，变化可以为正、负或真实的 0
- `NO_ASSETS`：当前指标范围为空；`TOTAL_ASSETS` 没有任何计入资产时适用，`NET_ASSETS` 仅在资产和负债均未计入时适用
- `PENDING_DATA`：当天尚未结束，行情、净值、汇率或投影仍待完成
- `PARTIAL`：部分资产缺少价格或汇率，完整变化不可用
- `UNAVAILABLE`：无法形成可靠的日初或日终资产值

只有 `CALCULATED` 可以返回变化金额；`PARTIAL` 和 `UNAVAILABLE` 不得把已估值小计伪装成完整总资产。月份存在任何待处理或不完整的应计算日期时，月度变化和变化率返回 null，并明确完整性状态。历史交易、价格、净值、汇率或计入设置修正后，自动重算受影响日期和月份，发布新的 `valuationRevision`，默认展示最新修订并保留旧版审计。

## 16. 离线能力和多端同步

移动端支持离线使用。

无网络情况下允许：

- 新增收入
- 新增支出
- 新增退款
- 新增转账
- 修改或删除尚未同步的本地数据
- 查看已经缓存的数据

涉及共享成员管理、导入、行情更新和已同步交易冲正等需要服务器最终确认的操作，在离线时不可完成，界面必须说明原因。

### 16.1 同步原则

系统采用 **Server Authoritative** 模型，服务器保存最终权威数据。

```text
本地 SQLite 写入数据和同步队列
→ 网络恢复
→ 客户端按游标拉取服务器增量
→ 客户端携带操作 ID、幂等键和版本号上传操作
→ 服务器校验权限、版本和账务不变量
→ 服务器原子提交并返回结果
→ 客户端更新本地状态和同步游标
```

### 16.2 同步标识和幂等

- 客户端创建数据时使用 UUID
- 每次写操作包含全局唯一的客户端操作 ID 和幂等键
- 同一操作重复上传只返回首次处理结果，不得重复生成流水或分录
- 增量同步使用服务器游标，不依赖客户端本地时间
- 删除或作废状态通过墓碑记录同步，不物理删除
- 一笔交易及其所有分录作为一个原子同步单元

V1 的统一幂等作用域为“主体 + API 主版本 + OpenAPI operationId + Idempotency-Key”。已认证写操作以当前已认证用户作为主体；`registerUser`、`resetPassword` 等公开写操作仍保留 `Idempotency-Key`，以同一请求中经既有规则规范化的邮箱计算版本化匿名主体。匿名主体只保存外部 HMAC-SHA-256 的 32 字节摘要和密钥版本，不能使用固定系统用户、可空 `user_id` 的共享作用域或原始邮箱；不得把验证码、密码或 Token 写入幂等记录。

同作用域同 Key 的请求必须比较规范化请求 Hash：相同 Hash 只重放首次安全结果，不同 Hash 稳定返回 `IDEMPOTENCY_KEY_REUSED`，不能因资源 ID、业务载荷或 `If-Match` 改变而复用 Key。最大客户端重试窗口为 24 小时，服务端最短重放保护期为 7 天；超过保护期且记录已安全清理后，同一 Key 可以作为新请求使用，客户端不得依赖其得到旧结果。

### 16.3 冲突处理

每个可修改实体包含版本号。客户端基于旧版本提交修改时，服务器拒绝覆盖并返回当前服务器版本。

客户端必须向用户展示冲突内容，并允许：

- 保留服务器版本
- 基于服务器最新版本重新应用本地修改
- 放弃本地修改

系统不得使用无提示的“最后写入者获胜”覆盖财务数据。

删除与修改冲突、共享账户多人同时修改和成员权限已被撤销等情况，都必须由服务器重新校验。权限已失效的离线操作不得写入服务器。

## 17. 周期账单

用户可以创建按日、周、月或年重复的收入、支出和转账模板。

模板至少包含金额、账户、分类、重复规则、开始日期和可选结束日期。到期时系统生成待确认记录；用户确认后才写入正式账务分录，避免因规则错误直接改变余额。

## 18. 安全、隐私和数据可靠性

### 18.1 传输和身份安全

- 所有外部通信使用 HTTPS
- 密码使用适合密码存储的强 Hash 算法并配置独立盐
- 登录、验证码和密码重置接口必须限流
- 邮箱验证码必须短时有效、一次性使用并限制尝试次数
- Token 必须支持过期、轮换和撤销
- API 必须校验用户身份、资源归属和共享账户成员权限

邮箱验证码固定窗口限流按请求用途分别计算：

| 维度 | 窗口与配额 |
| --- | --- |
| 邮箱 | 60 秒 1 次、1 小时 5 次、24 小时 10 次 |
| 来源 IP | 10 分钟 20 次、24 小时 100 次 |
| 设备 | 1 小时 10 次、24 小时 30 次 |

任一窗口超限即返回 `429 RATE_LIMITED`，`Retry-After` 取所有超限窗口的最长剩余时间；被拒绝请求也必须提交计数。PostgreSQL 是跨实例限流权威，IPv4/IPv6 在 HMAC 前统一转为规范二进制地址（IPv4 映射 IPv6 归一为 IPv4），限流桶主体只保存按用途、维度和规范化主体域分离后的 HMAC-SHA-256 32 字节摘要及密钥版本，不保存原始 IP、邮箱或 `deviceId`。当前和上一版本 HMAC 密钥在轮换期间都参与识别，上一版本至少保留 48 小时；密钥来自外部密钥配置，不进入数据库、仓库或日志。

验证码、邮箱和设备限流的占用、超限判定及新挑战写入必须遵守固定顺序并在一个数据库事务中完成。超限事务只提交计数，不创建挑战。通过限流后，新挑战、旧挑战替换和投递 outbox 事件原子写入；若验证码进入 outbox 载荷，必须使用应用层信封加密。限流桶在窗口结束或阻塞截止时间后至少保留 7 天，再由清理任务删除。

密码登录沿用同一限流事实表，但使用独立 `LOGIN_PASSWORD/LOGIN/AUTH_LOGIN_V1` 作用域和独立 HMAC 域；当前与上一 HMAC 密钥均参与识别，上一版本至少保留 48 小时。密码校验和状态判断只形成统一凭据结果；本阶段不创建会话、Token 或 Cookie，也不写入 users 失败计数或自动锁定账号。

会话 Access Token、Refresh Token、会话标识和签名私钥均属于高敏感凭据：数据库只保存刷新 Token 摘要和必要生命周期状态，Access Token 与原始刷新 Token 不得进入数据库、日志、异常、审计 metadata、outbox 或幂等记录。签名私钥及公钥由外部密钥设施注入；当前私钥签发，当前与上一公钥按受控 `kid` 验证，上一公钥停止签发后至少保留 24 小时。

### 18.2 客户端安全

- 移动端 Token 和敏感密钥存储于系统安全存储
- 本地数据库加密
- 生物识别只保护本地解锁和凭据读取
- 敏感数据不得明文写入普通日志、剪贴板或通知内容

### 18.3 服务端数据安全

- 敏感字段按数据分类进行静态加密
- 加密密钥与业务数据分离管理并支持轮换
- 日志和错误信息脱敏
- 关键账务和权限操作写入不可由普通用户修改的审计日志
- 文件导入必须限制类型和大小，并进行恶意文件和公式注入防护

公开写接口的匿名幂等主体使用独立于验证码限流的外部 HMAC 密钥，并以用途专属、长度前缀的稳定编码进行域分离；数据库、日志、异常和响应均不得出现原始匿名邮箱。轮换时当前及上一版本同时查询，上一版本至少保留完整的 7 天重放保护期；切换当前版本前必须排空或围栏仍以旧版本写入的实例，避免同一匿名主体在两个版本下并发创建两条记录。

### 18.4 数据权利和可靠性

V1 支持：

- 用户数据导出
- 账号注销申请和风险确认
- 服务端数据备份和恢复
- 会话和设备撤销

账号注销必须明确共享账户、审计记录和法定或安全保留数据的处理方式。共享账户数据不得因单个成员注销而被错误删除。

备份必须定期执行并进行恢复演练。恢复后需要校验交易、分录和账户余额的一致性。

## 19. 数据原则

### 19.1 金额、价格、数量和汇率

服务端使用 `BigDecimal`，数据库使用 `NUMERIC / DECIMAL`。禁止使用 `float / double` 保存或计算财务数值。

建议数据库最低精度：

| 数据 | 建议类型 | 规则 |
| --- | --- | --- |
| 金额 | `NUMERIC(24, 8)` | 展示时按币种最小单位舍入 |
| 证券数量 | `NUMERIC(28, 12)` | 支持基金小数份额 |
| 证券价格 | `NUMERIC(28, 12)` | 保留市场原始精度 |
| 汇率 | `NUMERIC(28, 12)` | 保存报价方向和时间 |
| 比例 | `NUMERIC(9, 6)` | 取值范围 0～1 |

V1 货币最小单位：CNY、USD、HKD、EUR 为 2 位小数，JPY 为 0 位小数。

舍入规则固定如下：

- 用户输入金额先按原字符串解析，禁止经过浮点数；超过币种最小单位精度的实际入账金额必须拒绝或由用户明确确认舍入
- LedgerEntry、手续费、税费和实际成交金额在入账时按对应币种最小单位使用 `HALF_UP` 舍入，并保存舍入后的值
- 基金份额、证券数量、价格和汇率最多保留 12 位小数，不在每个中间运算步骤反复舍入
- 持仓成本投影最多保留 8 位小数，平均成本最多保留 12 位小数；全部卖出时释放剩余全部成本，避免残留尾差
- 投资市值和多币种统计先使用完整允许精度计算并聚合，最后在报表快照或 API 输出边界按展示币种最小单位舍入一次
- 百分比和收益率单独保留 6 位小数，不使用货币精度

统计过程中不得使用已经格式化的展示值参与后续计算。

### 19.2 时间

- 服务端时间统一以 UTC 存储
- 用户输入和界面展示按用户时区处理
- 创建交易时根据用户输入或当时用户时区生成权威 `business_date`
- 已入账交易的 `business_date` 保持不变；修改业务日期必须通过交易修订
- 用户修改时区不重新划分历史交易的日、月、年归属
- 当前和未来默认日期及展示边界使用用户当前时区
- 所有行情和汇率都记录其对应时间及来源

### 19.3 账务不变量

系统始终满足：

- 每笔已确认交易的分录在对应币种内借贷平衡
- 账户余额等于截至目标时点的有效分录汇总
- 作废和修改通过版本及冲正记录完成
- 同一幂等键不会产生重复交易
- 交易、持仓、现金和负债相关变动原子提交
- Dashboard 与账户明细使用相同统计口径和数据截至时间

幂等记录不是账务事实：同一数据库事务必须同时提交幂等终态、业务事实、审计和 outbox，不能先提交 `PROCESSING` 再另开事务写入事实。请求格式、认证、CSRF、权限/不可见资源和限流失败不建立记录；稳定版本冲突和业务规则错误可安全重放，暂时性外部失败只能在无业务事实写入时进入可重试状态，数据库事务回滚不得遗留孤儿 `PROCESSING`。

## 24. V1 验收标准

### 24.1 账务正确性

- 每笔已确认交易的账务分录均满足对应币种内借贷平衡
- Dashboard、账户详情和账务分录在相同数据截至时间下金额差异为 0
- 期初余额、转账、投资本金、借款本金和还款本金不被错误计入日常收入或支出
- 修改和作废交易后，余额、收支和历史审计结果保持一致
- 共享比例和是否计入统计的修改不改变生效时间之前的历史结果

### 24.2 同步正确性

- 同一操作重复提交任意次数只产生一笔业务结果
- 网络中断后重试不会产生重复流水或孤立分录
- 旧版本修改会触发明确冲突，不会静默覆盖服务器数据
- 共享成员权限被撤销后，其未同步操作不能写入服务器
- 一笔交易的任意分录写入失败时，整笔交易回滚

### 24.3 导入正确性

- 相同文件或相同外部流水重复导入时不会生成精确重复流水
- 疑似重复必须由用户确认，不得自动删除已有数据
- 错误行显示可定位的失败原因
- 导入批次可以整体撤销，撤销后余额和统计恢复一致

### 24.4 投资和多币种正确性

- 持仓数量能够由有效投资交易完整重建
- 移动加权平均成本、已实现收益和未实现收益计算结果与验收样例一致
- Tushare Pro 股票、场内 ETF 和场外基金分别使用正确的收盘价或单位净值估值
- 相同产品和业务日期的数据重复同步不会生成重复价格快照
- Tushare Pro 调用失败、超限或无权限时会记录失败原因并支持手工价格兜底
- 缺失行情或汇率不会被静默当作 0 或 1
- 当前估值使用最新有效价格和汇率，历史趋势使用历史时点数据
- 行情、汇率及手工修正均展示来源和时间

### 24.5 性能和体验

在约定的 V1 标准测试环境下，以单用户 100 个账户、100,000 条流水和 1,000 个持仓价格快照为基准：

- Dashboard 服务端接口 P95 响应时间不超过 2 秒
- 普通流水列表服务端接口 P95 响应时间不超过 1 秒
- 10,000 行账单文件在 60 秒内完成解析和重复检测
- 用户进入首页后，无数据异常时可在 3 秒内看到核心指标；超时或失败必须展示明确状态和重试入口

性能验收不包含用户公网网络耗时，但包含数据库查询和服务端计算时间。

### 24.6 安全和恢复

- 未授权用户无法访问其他用户或未加入共享账户的数据
- OWNER、EDITOR、VIEWER 权限矩阵全部通过接口级测试
- 验证码、登录和密码重置接口具备限流和防暴力尝试措施
- 日志、错误信息和通知中不出现密码、Token、完整敏感凭据
- Tushare Token 不出现在客户端包、客户端请求、代码仓库或普通日志中
- 备份恢复演练后，交易、分录、账户余额和成员权限校验一致

### 24.7 可访问性

Web、iOS 和 Android 的注册登录、账户、交易、Dashboard、导入及错误恢复核心流程必须满足 WCAG 2.2 AA。至少保证键盘操作、可读标签和错误关联、不仅依赖颜色表达状态、图表文本替代，以及动态同步和冲突状态可被辅助技术感知。

## 25. 产品成功标准

第一版本不以“记了多少笔账”为核心指标，更关注：

### 数据完整性

用户主要资金账户的录入覆盖率，以及长期未更新账户的比例。

### 资产准确度

Dashboard 与账户明细、账务分录之间保持零口径差异；用户余额调整次数可用于识别数据维护问题。

### 使用成本

用户完成新增账户、记录流水、导入账单和处理冲突所需的步骤、时间及失败率。

### 更新频率

用户是否愿意持续更新资产，以及账户数据距离最近更新时间的时长。

### 核心体验

用户进入首页后，能够快速知道：

> 我现在有多少资产、资产在哪里、负债是多少，以及最近为什么发生变化。

## 26. 产品原则

后续新增或调整功能时，应优先判断它是否服务于以下目标：

1. 提高个人资产统计准确度。
2. 降低资金数据维护成本。
3. 帮助用户理解资产分布。
4. 帮助用户理解资产变化。
5. 提高投资资产统计准确度。

与以上目标关系较弱的能力，应降低优先级。

资迹的核心始终保持：

**个人资产总览，而不是复杂的传统记账系统。**
