# 资迹 Ziji — 需求追踪矩阵 RTM

**文档版本：** V0.1  
**对应产品版本：** V0.1  
**需求基线：** 《产品需求文档 PRD》V0.1  
**文档状态：** V1 正式设计基线

## 1. 文档目的

本矩阵把 PRD 拆分为可设计、可开发、可测试、可验收的原子需求，并建立以下追踪链：

```text
PRD 章节
→ 需求 ID
→ 领域/架构/数据库设计
→ API 契约
→ 测试用例
→ 验收结果
```

V1 的全部实施批次完成且本矩阵中所有 V1 需求达到“已验收”后，V1 才算完成。

## 2. 使用规则

### 2.1 需求 ID

| 前缀 | 领域 |
| --- | --- |
| AUTH | 注册、登录和用户设置 |
| ACC | 账户与余额 |
| LED | 流水与账务 |
| CAT | 分类和标签 |
| SHR | 共享账户 |
| IMP | 账单导入 |
| INV | 投资与行情 |
| LIA | 负债 |
| DASH | Dashboard 和统计 |
| FX | 多币种与汇率 |
| SYNC | 离线和多端同步 |
| REC | 周期账单 |
| SEC | 安全和隐私 |
| DATA | 数据原则 |
| OPS | 运维、性能和恢复 |

需求 ID 一经用于代码、接口或测试，不得复用。需求废弃时保留 ID 并标记“已废弃”。

### 2.2 状态

| 状态 | 含义 |
| --- | --- |
| 已确认 | PRD 已确认，尚未完成详细设计 |
| 已设计 | 领域、数据库和 API 已形成可实施设计 |
| 已实现 | 代码完成且通过开发验证 |
| 已验收 | 对应测试全部通过并由产品确认 |
| 已阻塞 | 依赖未满足，必须记录阻塞原因 |

当前项目尚未开始开发，跨文档设计基线已经评审通过，因此本版 V1 需求统一标记为“已设计”。

## 6. 变更流程

需求发生变化时必须依次完成：

1. 修改 PRD 并提升文档版本。
2. 新增或更新 RTM 需求 ID，禁止悄悄改写已实现需求含义。
3. 检查领域、架构、数据库和 API 的影响项。
4. 更新对应测试用例及验收门禁。
5. 在发布记录中保存需求版本和验收证据。
