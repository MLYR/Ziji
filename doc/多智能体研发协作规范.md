# 多智能体研发协作规范

## 1. 适用范围

本文是资迹 Ziji 项目的多智能体研发协作规则，由项目级 `AGENTS.md` 引用。它补充项目已有的安全、测试、任务台账、提交和架构约束，不替代这些约束。

## 2. 主会话与子智能体边界

- 主会话是唯一的任务发布者、依赖协调者、独立验收者、提交决策者和下一任务推进者。
- 子智能体只处理派发任务中明确授权的范围，必须遵守指定的文件、模块和职责边界。
- 子智能体开始工作前必须确认任务 ID、目标、验收条件、前置依赖、文件所有权、禁止触碰范围、测试要求和并行条件。
- 子智能体不得覆盖其他子智能体的修改；发现共享文件或依赖冲突时暂停并报告主会话。
- 子智能体不得自行执行 `git add`、`git commit`、`git push`、创建分支、创建 PR 或推进下一任务，除非主会话对该动作单独明确授权。
- 子智能体的自检结果不等同于独立验收结果；主会话必须重新检查变更范围、测试证据、任务台账、契约、权限和残余风险。

## 3. 角色分工

每个实现任务至少分配一个实施主角色和一个独立验收角色。实施角色不得兼任同一任务的独立验收角色。

| 任务类型 | 实施主角色 | 默认验收角色 |
| --- | --- | --- |
| 任务拆分、依赖、状态、发布顺序 | Project Shepherd | Code Reviewer 或 Test Automation Engineer |
| 后端边界、事务、数据库设计和模块 seam | Backend Architect | Code Reviewer |
| Java、SQL adapter、application/domain 实现 | Backend worker | Code Reviewer 或 Test Automation Engineer |
| API、OpenAPI 和契约变化 | Backend worker 或 API Tester | API Tester |
| 自动化、并发、回归和测试稳定性 | Test Automation Engineer | Code Reviewer |
| Web 页面和客户端能力 | Frontend Developer | Test Automation Engineer |
| Mobile 页面、Expo 和原生流程 | Mobile App Builder | Test Automation Engineer |
| 权限、认证、敏感数据和信息泄漏 | Application Security Engineer | Code Reviewer 或 Test Automation Engineer |
| 范围、质量、架构和可维护性审查 | Code Reviewer | 主会话 |
| 端到端、发布和验收证据 | Test Automation Engineer | 主会话 |

专项规则：

- API 或 OpenAPI 发生变化时必须加入 API Tester。
- 权限、认证、敏感数据或越权风险变化时必须加入 Application Security Engineer。
- 迁移、事务边界、数据库约束或跨模块架构变化时必须加入 Backend Architect 或 Code Reviewer。
- 高风险任务不要求所有验收角色同时参与；按实际风险增加专门验收角色。
- 跨领域任务先由 Project Shepherd 拆成可独立验收的子任务，再分别派发。

## 4. 并行与依赖

- 没有共享文件、共享接口、数据库迁移顺序、生成物或运行时依赖的子任务，默认并行派发。
- 存在同文件修改、接口先后关系、迁移版本关系、共享生成物或测试依赖时，必须串行执行。
- 并行数量受当前运行环境可用智能体槽位限制；不得为了并行拆分没有独立验收价值的工作。
- 并行任务完成后，主会话统一检查冲突、接口兼容性和集成风险，再进入验收阶段。

## 5. 模型风险分级

模型按任务风险和复杂度动态选择，不按角色永久绑定固定模型。

| 风险档位 | 默认模型 | 适用范围 |
| --- | --- | --- |
| 高 | GPT-5.6-sol，`high` 或 `xhigh` | 账务、余额、持仓、收益、权限、认证、幂等、同步、迁移、安全、跨模块架构和复杂并发 |
| 中 | GPT-5.6-terra，`medium` 或 `high` | 普通后端、API 契约、客户端功能、集成测试和中等复杂重构 |
| 低 | GPT-5.6-luna，`low` 或 `medium` | 文档、简单脚本、局部检查、机械性测试补充和低风险静态审查 |

- P0 任务默认使用高风险档位。
- 代码量小但涉及财务事实、权限边界、敏感数据或数据库迁移的任务仍按高风险处理。
- 子智能体失败、测试不稳定、跨模块影响扩大或独立审查发现重大风险时，主会话应升级模型档位。
- 本地路由器无法提供指定模型时，只允许使用同档位或更高档位的可用模型，不得静默降级。
- 模型选择、升级或替代原因写入任务派发记录或最终验收证据。

## 6. 派发格式与固定验收包

主会话派发子任务时必须包含：

1. 任务 ID、目标和验收条件。
2. 实施角色、验收角色和模型风险档位。
3. 前置依赖、允许修改的文件/模块和禁止触碰范围。
4. 预期测试、验证命令和并行/串行条件。
5. 交付格式和失败升级路径。

子智能体完成后必须回传：

- 已完成内容和未完成内容；
- 实际修改的文件、模块和接口；
- 前置依赖是否满足；
- 执行的测试/检查命令和结果；
- 未执行的验证及原因；
- 已知风险、假设和潜在回归点；
- 是否建议转入 `REVIEW`；
- 是否需要追加 Code Reviewer、Test Automation Engineer、API Tester 或 Application Security Engineer。

## 7. 验收、提交与任务推进

- 主会话必须独立检查子智能体交付物，确认范围、行为、测试和安全边界均符合任务 DoD。
- 未完成独立验收时，不得把任务标记为 `DONE`，不得把子智能体报告直接作为验收证据。
- 主会话完成验收后，按项目任务台账推进 `REVIEW`、`VERIFYING` 和 `DONE` 状态。
- 主会话只有在用户明确授权提交时，才能执行 `git add`、`git commit`、`git push` 或创建 PR；子智能体默认不拥有这些权限。
- 当前任务未完成验收时，不得擅自进入依赖它的下一任务；已明确独立且无依赖的任务可以并行启动。
- 提交信息、测试证据和任务台账必须能对应到实际完成的子任务。
