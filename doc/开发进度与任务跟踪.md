## 1. 文档目的

本文是 V1 开发的唯一总任务台账，管理从设计、工程初始化、编码、测试到发布的全部工作。RTM 回答“需求是否被设计、实现和验收”，本文回答“谁在做什么、做到哪里、依赖什么、如何证明完成”。

所有开发工作必须先在本文登记再开始。开发中发现的缺陷、返工、迁移、脚本、测试、文档和运维动作，不论大小，都必须新增独立任务或子任务；不得只在聊天、提交信息或个人笔记中存在。

## 2. 管理规则

### 2.1 四级任务结构

```text
EPIC 大阶段
└── FEATURE 功能或工作包
    └── TASK 可独立交付的任务
        └── SUBTASK 完成 TASK 所需的具体动作
```

- 本文的章节表示 EPIC，三级标题表示 FEATURE，表格每一行表示可追踪的 TASK 或 SUBTASK。
- `父任务` 指向直接上级 FEATURE 或 TASK；父任务状态根据最底层任务汇总，不单独计入进度。
- 最底层任务应当能够独立验证，目标工作量通常为 0.5～2 个工作日；超过 2 个工作日必须继续拆分。
- 一个任务如果同时包含后端、Web、移动端和测试，必须拆成不同任务，避免“完成了一部分”却无法准确更新状态。
- 新发现的工作使用新的任务 ID；任务 ID 一经引用不得复用或改写成无关含义。

### 2.2 状态

| 状态 | 含义 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| `BACKLOG` | 已登记，尚未满足开始条件 | 范围和交付物已明确 | 前置依赖满足后转 `READY` |
| `READY` | 可以立即开始 | 需求、设计和依赖齐备 | 开始工作后转 `IN_PROGRESS` |
| `IN_PROGRESS` | 正在实施 | 已有负责人并开始产出 | 转评审、验证或阻塞 |
| `BLOCKED` | 无法继续 | 有明确外部依赖或决策缺口 | 阻塞解除后返回原流程 |
| `REVIEW` | 等待代码、设计或产品评审 | 产出已完成且自检通过 | 评审通过后转 `VERIFYING` |
| `VERIFYING` | 正在测试或验收 | 已具备可验证产物 | 全部验收条件通过后转 `DONE` |
| `DONE` | 已完成并有证据 | 实现、测试、文档均满足 DoD | 需求变更时新增返工任务，不回写历史 |
| `DEFERRED` | 已确定延后版本 | 不属于 V1 或本期明确不做 | 后续版本重新排期 |
| `CANCELLED` | 已取消 | 有明确取消决策和原因 | 保留记录，不再执行 |

### 2.3 优先级与批次

| 优先级 | 定义 |
| --- | --- |
| P0 | 不完成则无法继续开发、造成财务错误、数据丢失或越权 |
| P1 | V1 核心闭环或发布门禁 |
| P2 | V1 重要能力，但不阻塞其他大部分任务 |
| P3 | 体验优化、工具改善或非关键增强 |

| 批次 | 范围 |
| --- | --- |
| B0 | 设计基线和工程基础，不计入 PRD 四个业务批次 |
| B1 | 核心账户、账务、负债、分类、基础 Dashboard 与基础同步 |
| B2 | 共享账户和账单导入 |
| B3 | 投资、Tushare、持仓和收益 |
| B4 | 多币种、周期账单、安全、数据权利和运维闭环 |
| ALL | 跨批次测试、发布和项目管理 |

### 2.4 完成定义（Definition of Done）

TASK 只有同时满足以下条件才能标记 `DONE`：

1. 交付物已经落入仓库或指定外部系统，且不存在未说明的占位实现。
2. 贴近改动点的单元、集成、契约或端到端测试通过，并填写验收证据。
3. OpenAPI、Flyway、生成类型、RTM 和本文等受影响基线已同步。
4. 权限、幂等、审计、精度、时区和失败路径已按任务风险完成检查。
5. 评审意见已处理；残余风险已记录且由相应责任人接受。

### 2.5 进度算法

- 只统计最底层、属于 V1 且状态不是 `DEFERRED/CANCELLED` 的任务。
- 每个最底层任务权重为 1；`DONE` 计 1，其余状态计 0，避免主观填写“完成 80%”。
- EPIC、FEATURE、批次和工作流进度均为 `DONE 叶子任务数 ÷ 有效叶子任务总数`。
- 设计完成不等于功能完成；设计任务和实现任务分别计数。
- 本文的汇总数字在每次状态更新后必须一并重算。

## 12. 任务更新流程

### 12.1 每次开发必须执行

1. 开始前确认任务已存在、依赖满足，将唯一一个当前任务改为 `IN_PROGRESS` 并填写负责人。
2. 新发现的子工作、缺陷或返工先分配新 ID；如果阻塞原任务，原任务改为 `BLOCKED` 并填写原因。
3. 产出完成且自检通过后转 `REVIEW`；评审通过后转 `VERIFYING`。
4. 验证通过后填写产出物、测试命令或证据链接，再转 `DONE`；同时更新 RTM 状态。
5. 重算第 3 节汇总，更新最后更新时间，并在第 14 节追加变更记录。

### 12.2 新任务模板

```text
任务 ID：<工作流>-<领域>-<三位序号>
父任务：
任务名称：
状态：BACKLOG
优先级：P0/P1/P2/P3
批次：B0/B1/B2/B3/B4/ALL
负责人：未分配
前置依赖：
需求来源：PRD / RTM ID
设计来源：领域 / 架构 / DB / API 章节
验收依据：T-* 或可验证条件
产出物：
计划开始：
计划完成：
实际完成：
阻塞原因：
备注：
```

### 12.3 缺陷与需求变更

- 缺陷 ID 使用 `BUG-<领域>-NNN`，必须关联发现该缺陷的测试、受影响任务和 RTM 需求。
- S0/S1 缺陷优先级为 P0，修复和回归必须是两个可追踪子任务；未关闭时阻塞发布。
- 需求变更先更新 PRD 和 RTM，再建立 `CHG-<领域>-NNN` 影响分析任务，随后新增实现与回归任务。
- 已完成任务不回写成新的含义；废弃产出通过 `CANCELLED` 变更任务和新替代任务保留历史。
